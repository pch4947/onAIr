# 엔진 튜닝 절차

**대상**: `apps/engine` — 설정값(`config/chat_rules.yaml`, 엔진 설정), 프롬프트(`corners/`), 편성·선별 코드
**상태**: 초안 v0.1 (2026-11-10)
**함께 보는 문서**: 실험 기록 [ENGINE_TUNING_LOG.md](ENGINE_TUNING_LOG.md), 명령과 출력 형식 [apps/engine/README.md](../apps/engine/README.md), 지표 정의 [CORNER_DESIGN.md](CORNER_DESIGN.md) 9.5절

엔진의 무엇을 바꿀 때 어떤 근거로 채택하는지를 정한다. 보고서의 평가 방법 절은 이 문서를, 결과 절은 실험 기록을 옮겨 쓴다(7절).

---

## 1. 왜 절차를 바꿨나

시나리오 실행기(`onair-scenario`)는 회차마다 기대 결과(`expect`)의 통과 여부를 판정한다. 이 판정은 "최대 무음 10초 이하"처럼 문턱을 넘었는지만 본다. 문턱을 넘은 뒤에는 9초와 0초가 같은 값이라 더 나아질 방향이 보이지 않고, 넘은 것처럼 보이게 하는 변경과 실제로 나아진 변경을 가르지 못한다.

그래서 문턱 판정은 회귀 확인용으로 남기고, 변경을 채택하는 근거는 **지금 설정과 견준 차이**로 바꿨다. 목표치가 없으므로 더 나은 변경이 나오는 한 계속 갱신할 수 있다.

기계학습의 학습 루프에 견주면 다음과 같다. 엔진의 LLM은 API 뒤에 있어 기울기를 구할 수 없으므로, 가중치를 직접 고치는 방식은 쓸 수 없다.

| 학습 루프 | 이 절차 |
|---|---|
| 가중치 | 설정값, 프롬프트 문구, 편성·선별 코드 |
| 순전파 | 시나리오 실행 한 회차, 또는 대본 평가 한 번 |
| 손실 | 지금 설정과 짝지어 견준 지표 차이 |
| 갱신 | 사람이나 코딩 에이전트가 실패 대본을 읽고 낸 수정안 하나 |
| 검증 세트 | 튜닝에 쓰지 않는 시나리오(`config/scenarios/holdout/`) |

## 2. 원칙

1. **원인을 먼저 가른다.** 증상이 구조에서 오는지, 수치에서 오는지, 프롬프트에서 오는지 정한 뒤에 손댄다. 구조 문제는 값을 훑어도 움직이지 않는다.
2. **손잡이마다 가장 싼 평가를 쓴다.** 수치는 더미 LLM으로, 프롬프트는 실시간이 아닌 대본 평가로 본다. 실제 LLM으로 30분을 도는 통합 실행은 검증에만 쓴다.
3. **절대 점수가 아니라 지금 설정과 견준다.** 같은 seed의 회차끼리, 같은 자리의 대본끼리 짝짓는다.
4. **한 번에 하나만 바꾼다.** 둘을 같이 바꾸면 어느 쪽이 지표를 움직였는지 알 수 없다.
5. **튜닝에 쓴 시나리오로 검증하지 않는다.** 시나리오가 다섯 개이고 채팅 문장이 고정이라, 같은 시나리오로 계속 고치면 그 문장에만 맞는 엔진이 된다.
6. **실험 조건은 튜닝하지 않는다.** 선별 기준, 인용 창(`reaction_window_sec`), 집계 언급 여부는 사용자 실험의 조작 변수다(CORNER_DESIGN 10절). 값을 훑어 곡선을 얻는 것은 괜찮지만 한 값으로 굳히면 조건 비교가 흐려진다.
7. **모든 실행은 재현 정보와 함께 남긴다.** 도구가 자동으로 남기는 것과 사람이 적는 것을 5절과 6절에 나눠 적었다.

## 3. 절차

### 3.1 원인 분류

실제 LLM으로 돌린 통합 실행의 대본을 읽고 증상을 모은다. 대본 검토 페이지(`review.html`)에서 멘트마다 증상 분류와 메모를 달고 `issues.csv`로 내보낸다. 그다음 증상마다 원인이 어느 층인지 정한다.

| 원인 층 | 뜻 | 가리는 방법 | 고치는 곳 |
|---|---|---|---|
| 구조 | 편성 순서, 버퍼, 대기 방식에서 온다 | 엔진 이벤트(`events.jsonl`)에서 시간이 어디서 흘렀는지 본다. 더미 LLM으로도 똑같이 생긴다 | 코드 (이슈를 따로 연다) |
| 수치 | 창, 문턱, 한도 값에서 온다 | 값을 바꾼 변형에서 지표가 움직인다(3.2절) | `chat_rules.yaml`, 엔진 설정 |
| 프롬프트 | LLM이 지시를 다르게 따른다 | 더미 LLM에서는 생기지 않고 실제 LLM에서만 생긴다. 같은 입력에서 대본만 다르다 | `corners/steps.py`, `corners/base.py`, persona |
| 도구 | 실행기나 시나리오가 실제와 다르다 | 실제 방송이나 실제 TTS 회차에서는 생기지 않는다 | `scenario/`, 시나리오 파일 |

예: 2026-11-07 demo 회차에서 0:40에 온 채팅이 5:07에 방송됐다. 이벤트를 보면 선별은 도착 27초 뒤에 끝났고, 나머지 4분은 그 사이에 나간 곡(3분 32초)과 문자 코너를 기다린 시간이다. 선별 창이나 문턱을 바꿔도 줄지 않으므로 구조로 분류한다.

### 3.2 수치 튜닝

더미 LLM으로 지금 설정(`base`)과 변형을 같은 seed로 함께 돌린다. API를 쓰지 않으므로 비용이 없고, 동시 실행 수는 실행기의 루프 지연이 허용하는 만큼 올릴 수 있다(8절).

```powershell
python -m onair_engine.scenario config/scenarios/sparse.yaml config/scenarios/flood.yaml --llm dummy `
  --sweep standalone_window_sec=300,900 --repeat 10 --parallel 60 --note "독립형 창이 반영률에 주는 영향"
```

- 실행이 끝나면 `compare.md`에 `base` 대비 변형마다 지표 차이와 판정이 나온다.
- 값은 가장 높은 한 점이 아니라 **주변 값에서도 결과가 비슷한 구간**에서 고른다. 한 점에서만 좋은 값은 시나리오에 맞춰진 값이다.
- 더미 LLM은 넣으라는 채팅을 항상 인용한다. 실제 LLM은 빠뜨리기도 하므로(8절) 반영률의 절대값은 실제보다 높다. 변형 사이의 차이를 보는 데 쓰고, 채택 전에 3.4절의 실제 LLM 검증을 거친다. 누락을 넣어 보려면 `--set sim.llm_quote_miss_rate=0.5`를 쓴다.
- 지표가 어느 변형에서도 움직이지 않으면 그 증상은 수치 문제가 아니다. 그 결과도 기록한다.

### 3.3 프롬프트 튜닝

대본 평가(`onair-eval`)는 고정 사례로 생성 파이프라인만 돌리므로 실시간을 기다리지 않는다. 고치기 전과 고친 뒤에 같은 조건으로 한 번씩 돌리고, 두 결과의 대본을 쌍으로 견준다.

```powershell
python -m onair_engine.eval --repeat 2                       # 고치기 전 → var/eval/<A>
# 프롬프트 문구를 하나 고친다 (커밋하지 않아도 worktree.diff로 남는다)
python -m onair_engine.eval --repeat 2                       # 고친 뒤 → var/eval/<B>
python -m onair_engine.eval.pairwise var/eval/<A> var/eval/<B>
```

- 같은 persona·회차·단계의 대본 두 개를 어느 쪽이 고친 뒤인지 가리고 순서를 섞어 보여 준다. 심사는 나은 쪽을 고르거나 같다고 답한다.
- 심사는 세 가지로 할 수 있다. 어느 쪽이든 `pairs.md`만 보고 고른다.
  - 사람: `votes.csv`를 채우고 `--tally`로 집계한다. 보고서의 사람 평가로 쓸 수 있다.
  - 코딩 에이전트(Claude Code 등): 세션에서 `pairs.md`를 읽고 `votes.csv`를 채운다. 구독 안에서 돌아 API 과금이 따로 없다.
  - LLM: `--judge-llm`. 생성에 쓴 모델과 다른 모델을 쓴다.
- 쌍 비교는 자연스러움, persona 일치, 소재 충실도를 본다. 길이 초과나 말투 이탈 같은 규칙 위반은 집계 결과의 자동 지표 표(전·후)로 따로 확인한다.
- 사람이 아닌 심사는 사람의 선택과 가끔 맞춰 본다. 같은 쌍을 사람이 골라 일치율을 기록해 두면 그 심사를 어디까지 믿을지 근거가 된다.

### 3.4 통합 검증

채택하려는 변경은 실제 LLM으로 검증용 시나리오를 돌려 확인한다.

```powershell
python -m onair_engine.scenario config/scenarios/holdout/commute.yaml config/scenarios/holdout/rain.yaml --yes --note "T-00N 검증: 수정 전"
# 변경 적용
python -m onair_engine.scenario config/scenarios/holdout/commute.yaml config/scenarios/holdout/rain.yaml --yes --note "T-00N 검증: 수정 후"
python -m onair_engine.scenario.compare var/scenario/<전> var/scenario/<후>
```

- 여기서는 개선을 찾지 않는다. **악화가 없는지**와 목표 지표가 같은 방향으로 움직이는지만 본다.
- 설정값 변경은 `--sweep`으로 전·후를 한 번에 돌릴 수 있다.
- 검증용 시나리오를 보고 값을 다시 고치기 시작하면 그 시나리오는 더 이상 검증용이 아니다. 새 시나리오를 추가한다.
- 대본이 달라지는 변경은 실제 TTS 회차(`--tts gemini --repeat 1`)를 하나 들어 본다. 지표가 좋아져도 귀로는 나빠질 수 있다.

### 3.5 기록

변경 하나마다 [ENGINE_TUNING_LOG.md](ENGINE_TUNING_LOG.md)에 항목 하나를 쓴다. 채택하지 않은 변경도 쓴다(6절).

## 4. 판정 기준

- **목표 지표를 실행 전에 적는다.** 비교 표에는 지표가 스무 개쯤 나온다. 5% 기준으로 하나씩 보면 아무것도 바꾸지 않아도 하나쯤은 넘는다. 실험 기록의 "목표 지표"에 먼저 적은 것으로 판정하고, 나머지는 부작용 확인에 쓴다.
- **시나리오 비교**(`onair-compare`): 같은 seed 회차끼리의 차이 평균이 회차 간 흔들림을 넘을 때만 개선·악화로 적는다(짝 t 검정, 양쪽 95%). 3쌍 미만은 판정하지 않는다.
- **대본 쌍 비교**(`onair-pairwise`): 같음을 뺀 선택이 한쪽으로 치우쳤을 때만 낫다고 적는다(부호 검정, p < 0.05). 6쌍 미만은 판정하지 않는다 — 다섯 번을 다 이겨도 p = 0.06이다.
- **회차 수**: 같은 조건으로 돌린 실행을 `onair-compare <폴더>`에 넣으면 지표별 "구분되는 차이"가 나온다. 기대하는 개선 폭이 그보다 작으면 회차를 늘린다. 실제 LLM은 대본이 매번 달라 seed를 맞춰도 흔들림이 크므로 5회 이상을 권한다.
- **짝짓기의 한계**: seed를 맞춰도 실시간 실행이라 두 회차의 경로가 갈린다. 값이 같은 변형끼리 견준 실행(실험 기록 T-002, 더미 LLM, 10쌍)에서 짝짓기는 세그먼트 생성 시간의 흔들림을 1/4~1/11로 줄였지만 반영률과 반영 시간은 1/1.5~1/2로 줄이는 데 그쳤다. 반영 지표를 목표로 삼을 때는 회차를 더 잡는다.
- **채택 조건**: 목표 지표가 개선이고, 다른 지표에 악화가 없고, 검증용 시나리오에서 악화가 없다. 셋 중 하나라도 아니면 기각으로 기록한다.
- **차이 없음도 결과다.** 기각한 변경과 움직이지 않은 값은 "이 손잡이는 이 증상과 무관하다"는 근거가 된다.

## 5. 도구가 남기는 기록

실행 결과는 `apps/engine/var/` 아래에 쌓인다. 이 폴더는 git에 올리지 않으므로 보고서 근거가 된 실행은 지우지 않는다.

| 파일 | 내용 | 쓰임 |
|---|---|---|
| `var/scenario/<시각>/session.json` | 명령, 커밋, 커밋하지 않은 변경 여부, 변형과 덮어쓴 값, LLM, 목적(`--note`), 루프 지연 | 실험 기록의 "실행" 칸이 가리키는 곳 |
| `var/scenario/<시각>/worktree.diff` | 커밋하지 않은 엔진 변경 | 프롬프트를 고쳐 보는 중의 실행을 다시 만든다 |
| `…/run-N/run.json` | 시나리오 원문, seed, 변형, LLM | 회차 하나의 재현 |
| `…/run-N/report.json`, `events.jsonl`, `transcript.md` | 지표 원자료, 엔진 이벤트, 대본 | 원인 분류의 근거, 보고서에 인용할 대본 |
| `var/scenario/<시각>/compare.md`, `compare.json` | `base` 대비 변형의 지표 차이와 판정 | 실험 기록에 붙이는 표 |
| `var/scenario/ledger.jsonl` | 실행마다 변형 × 시나리오 한 줄 — 지표 평균·표준편차, 커밋, 설정 | 기간 전체의 추이 그래프, 실행 목록 |
| `var/eval/<시각>/run.json`, `worktree.diff` | 대본 평가의 커밋, LLM, 사례 파일 | 쌍 비교의 전·후가 어느 코드인지 |
| `var/pairwise/<시각>/report.md`, `votes.csv`, `key.json` | 쌍 비교 판정, 쌍별 선택과 메모, 가린 순서 | 실험 기록에 붙이는 표, 사람 평가 원자료 |

## 6. 사람이 남기는 기록

도구는 숫자와 출처를 남긴다. 왜 바꿨고 어떻게 판단했는지는 사람이 적는다.

- **실험 기록**([ENGINE_TUNING_LOG.md](ENGINE_TUNING_LOG.md)): 변경 하나에 항목 하나. 증상, 원인 층, 가설, 목표 지표, 변경, 실행, 결과 표, 판정을 적는다. 양식은 그 문서 머리에 있다.
- **값의 출처**: 실험으로 정한 값은 설정 파일의 주석을 `[임시값]`에서 `[실험 T-00N]`으로 바꾼다. 값만 보고도 근거를 찾아갈 수 있다.
- **커밋과 PR**: 채택한 변경의 커밋 메시지나 PR 본문에 항목 번호를 적는다.
- **열린 관찰**: 아직 원인을 가르지 못한 증상은 실험 기록의 "열린 관찰"에 적어 둔다. 다음 튜닝의 출발점이다.

| 최종 설정값과 근거 | `chat_rules.yaml`의 `[실험 T-00N]` 주석과 해당 항목 |
| 지표 추이 | `ledger.jsonl` |
| 사람 평가 | 쌍 비교의 `votes.csv`와 `report.md`, 대본 검토 페이지의 표시 CSV |
| 대본 예시 | 항목에 인용한 `transcript.md` 구절 (실행 시각과 회차 번호를 같이 적는다) |

보고서에 수치를 옮길 때는 회차 수, LLM 모델, 커밋을 함께 적는다. 비교 표의 머리에 이 정보가 들어 있다.

## 8. 흉내의 한계

이 절의 내용은 보고서의 평가 환경 절에 그대로 들어가야 한다.

- **실시간 실행**: 엔진의 인용 창, 버퍼 판단, 방송 종료가 실제 시계로 돌기 때문에 시간을 압축하지 않는다. 30분 방송은 30분 걸린다.
- **TTS 흉내**: 길이는 글자 수에 비례하고 지연은 2026-11-02 Gemini 실측 두 점을 이은 식이다. 말 속도(`tts_chars_per_sec`)는 `[임시]` 값이다. 타이밍 수치를 이 흉내에 끝까지 맞추면 실제 TTS에서 어긋날 수 있다.
- **더미 LLM**: 지연은 2026-11-07·10 시나리오 실행 실측(gpt-6-luna low, 호출 456건: 평균 1.5~1.6초, 표준편차 0.4초)에 맞췄다. 대본은 단계별 고정 문장이라 대본 품질 지표(같은 첫머리, 유사도)는 뜻이 없다. 넣으라는 채팅을 항상 인용하는데, 같은 실측에서 실제 LLM은 채팅 인용 38건 중 19건을 빠뜨렸다(문자 낭독 24건은 모두 들어갔다).
- **동시 실행**: 모든 회차가 한 프로세스의 이벤트 루프에서 돈다. 루프가 밀리면 타이머가 늦게 깨어나 생성 시간과 반영 시간이 길게 재진다. 회차마다 루프 지연을 재고(`loop_lag_ms_p95`) 250ms를 넘으면 경고한다. 더미 LLM으로 flood 30분 방송을 동시 60회 돌렸을 때 타이밍 지표는 동시 4회와 같았다(실험 기록 T-001). 실제 LLM 실행은 한 번에 하나만, 동시 35회 이하로 돌린다 — 두 실행을 겹쳐 돌리자 시작 뒤 5분의 LLM 응답이 늦어져 생성 시간이 2~4초 길게 재졌고, 루프 지연 경고는 이것을 잡지 못했다(T-004).
- **판정의 오경보**: 값이 같은 변형끼리 견준 실행에서 방향이 있는 지표 29개 중 개선·악화 판정은 0개였다(실험 기록 T-002).
- **심사의 편향**: LLM 심사는 자기 모델의 대본을 고르는 경향과 먼저 보인 쪽을 고르는 경향이 있을 수 있다. 다른 모델을 쓰고, 순서를 섞고, 먼저 보인 쪽을 고른 비율을 집계에 같이 낸다.
- **시나리오 수**: 튜닝용 5개, 검증용 2개다. 주제와 채팅 문장이 적어 여기서 얻은 수치는 그 범위 안의 근거다.
- **재지 않는 것**: Redis 전송, HLS 플레이어 지연, 실제 발음, 청취자가 느끼는 소통감. 마지막 것은 사용자 실험이 잰다.
