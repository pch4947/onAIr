# 엔진 튜닝 기록

엔진의 설정값·프롬프트·코드를 바꾼 근거를 변경 하나에 항목 하나로 남긴다. 절차와 판정 기준은 [ENGINE_TUNING.md](ENGINE_TUNING.md)에 있다.

- 항목은 번호(T-001부터)를 붙이고 위에서 아래로 쌓는다. 지난 항목은 고치지 않고, 뒤집히면 새 항목에서 가리킨다.
- **채택하지 않은 변경도 적는다.** 움직이지 않은 값과 효과가 없던 수정은 "이 손잡이는 이 증상과 무관하다"는 근거다.
- 목표 지표는 실행하기 전에 적는다.
- 결과 표는 도구가 만든 것(`compare.md`, 쌍 비교 `report.md`)을 붙인다. 표 머리의 출처(실행 폴더, 커밋, LLM)를 지우지 않는다.
- 실행 폴더는 `apps/engine/var/` 아래에 있고 git에 올라가지 않는다. 항목이 가리키는 폴더는 지우지 않는다.

## 양식

```markdown
### T-00N 제목 (YYYY-MM-DD) — 채택 | 기각 | 보류

- **증상**: 무엇이 문제였나. 대본이나 이벤트를 인용하고 실행 시각·시나리오·회차를 적는다
- **원인 층**: 구조 | 수치 | 프롬프트 | 도구 — 그렇게 본 근거
- **가설**: 무엇을 바꾸면 어떤 지표가 어느 쪽으로 움직일 것인가
- **목표 지표**: 판정에 쓸 지표와, 나빠지면 안 되는 지표
- **변경**: 바꾼 값 또는 커밋·PR
- **실행**: 명령, 실행 폴더, 회차 수, LLM
- **결과**: 비교 표
- **판정**: 채택·기각과 이유. 검증용 시나리오 결과
- **남은 것**: 이 항목이 답하지 못한 것
```

## 기준선

아직 없다. `main`에서 실제 LLM으로 튜닝용 시나리오 5개와 검증용 2개를 5회씩 돌리고, `onair-compare <폴더>`의 회차 간 편차 표를 여기에 붙인다. 이후 항목의 "수정 전"은 이 실행과 견준다. 동시 실행 수(`--parallel`)는 LLM 제공자의 분당 한도에 맞춘다.

```powershell
python -m onair_engine.scenario config/scenarios/quiet.yaml config/scenarios/sparse.yaml config/scenarios/demo.yaml `
  config/scenarios/flood.yaml config/scenarios/adversarial.yaml `
  config/scenarios/holdout/commute.yaml config/scenarios/holdout/rain.yaml --note "기준선"
```

참고로 2026-11-10 실행(`20261110-095531`, 커밋 9171441, gpt-6-luna, 3회)의 편차를 보면, 독립형 반영률은 표준편차가 demo 0.58, sparse 0.38이다. 3회로는 0.87 넘게 달라져야 구분된다 — demo는 채팅이 1건, sparse는 4건이라 한 건의 반영 여부가 비율을 크게 흔든다. 이 지표를 목표로 삼으려면 회차를 늘리거나 채팅이 많은 시나리오를 써야 한다.

## 열린 관찰

원인 층을 아직 가르지 못한 증상이다. 항목으로 옮기면 여기서 지운다.

### O-001 넣으라고 준 채팅이 대본에서 빠진다 (2026-11-10)

- 실제 LLM 실행 두 번(`20261107-181456` 커밋 7f7bf2f, `20261110-095531` 커밋 9171441, gpt-6-luna low, demo·quiet·sparse 3회씩)의 인용 검사 기록을 세었다.
- 문자 낭독(문자 소개 코너)은 24건이 모두 대본에 들어갔다. 채팅 인용(오늘의 이야기, 곡 소개, 엔딩)은 38건 중 19건이 빠졌다.

  | 실행 | 오늘의 이야기 | 곡 소개 | 엔딩 |
  |---|---|---|---|
  | 2026-11-07 | 7건 중 4건 누락 | 8건 중 4건 누락 | 3건 중 1건 누락 |
  | 2026-11-10 | 11건 중 6건 누락 | 9건 중 4건 누락 | 없음 |

- 채팅마다 누락 비율이 다르다. 주제에 맞는 말은 한 번도 빠지지 않았고, DJ에게 묻는 말과 주제 밖의 말이 빠졌다.

  | 채팅 | 인용됨 | 누락 |
  |---|---|---|
  | 붕어빵은 팥이죠 | 6 | 0 |
  | 오늘 너무 피곤해요 | 7 | 4 |
  | 저도 퇴근 중이에요 | 3 | 6 |
  | DJ님은 겨울 간식 뭐 좋아하세요? | 3 | 9 |

- 빠진 채팅은 한 번 되돌렸다가 또 빠지면 거절된다. 그렇게 거절된 채팅이 다섯 건이다 — 2026-11-07 sparse 2회차 1건, 2026-11-10 demo 3회차 1건, sparse 1회차 1건, sparse 3회차 2건. sparse의 "DJ님은 겨울 간식 뭐 좋아하세요?"가 그중 세 건이다.
- 2026-11-10 demo의 기대 결과 "휴대폰으로 보낸 채팅이 3분 안에 들린다"가 2/3인 것도 이 때문이다. 1·2회차는 33초, 35초 만에 방송됐고 3회차는 두 번 빠져 거절됐다.
- 가를 것: LLM이 채팅을 실제로 건너뛰었는지(프롬프트), 질문에 답만 하거나 풀어서 말했는데 검사가 못 알아봤는지(검사 기준 `QUOTE_MATCH`). 누락된 세그먼트의 대본을 읽으면 갈린다.
- 막힌 곳: 지금 기록으로는 누락된 생성 작업과 그 대본을 이을 수 없다. `generation_log`에는 `job_id`만, `aired_log`에는 `segment_id`만 있다. 인용 검사 결과에 세그먼트 번호나 대본을 같이 남겨야 한다.
- 이 실행들의 `report.json`에는 인용 누락률이 없다(지표를 그 뒤에 넣었다). 위 수치는 회차별 `metrics.sqlite`의 `generation_log`에서 `stage = 'quote'`인 줄을 센 것이다.

### O-002 flood 회차의 계측 DB가 30분에 67MB까지 커진다 (2026-11-10)

- 더미 LLM으로 돌린 flood 30분 회차(`var/par-high/20261110-121446/flood/run-1`)의 `metrics.sqlite`가 67MB다. 같은 날 실제 LLM demo 회차는 1.4MB였다.
- 거의 전부 `decision_log`다. 2,923줄 가운데 2,885줄이 기다림 판단이고, 줄마다 그때의 인용 후보 전체(많을 때 110건, 약 30KB)를 `context_json`에 적는다(`scheduler.py`의 `pending_requests=list(self.pool.items)`).
- 영향: flood 60회차 실행 하나가 디스크 4GB를 쓴다. 실제 방송에서도 채팅이 몰리면 초당 한두 번 수십 KB를 SQLite에 커밋한다. T-001에서 본 디스크 동기화 대기가 방송 하나 안에서 얼마나 되는지는 재지 않았다.
- 가를 것: 기다림 판단마다 후보 전체가 분석에 필요한지, 건수만 남겨도 되는지.

## 기록

### T-001 실행기: 동시 실행이 타이밍 지표를 튼다 (2026-11-10) — 채택

- **증상**: 더미 LLM으로 flood를 동시 60회 돌리자 같은 seed의 회차가 동시 4회일 때와 다른 값을 냈다. 세그먼트 생성 P95가 11.5초에서 23.5초로, 반영 시간 중앙값이 28.8초에서 47.2초로 늘었다(4쌍 모두 같은 방향).
- **원인 층**: 도구. 엔진은 계측 기록마다 SQLite에 커밋하고, SQLite는 커밋마다 디스크 동기화를 기다린다. 회차가 모두 한 이벤트 루프에서 돌기 때문에 그 대기가 다른 회차의 타이머까지 막는다. 방송 준비(접착 문구 렌더링)가 한꺼번에 시작되는 것도 겹쳤다. 엔진 하나만 도는 실제 방송에서는 생기지 않는다.
- **가설**: 회차의 계측 DB를 디스크 동기화 없이 쓰고 회차를 간격을 두고 띄우면, 동시 실행 수와 무관하게 같은 seed가 같은 값을 낸다.
- **목표 지표**: 실행기 루프 지연 P95(새로 넣은 지표). 동시 4회와 60회의 짝 비교에서 세그먼트 생성 P95와 반영 시간 중앙값이 차이 없음.
- **변경**: `scenario/runner.py` — 회차 DB를 `PRAGMA synchronous=OFF`로 미리 만들고 연다, `--stagger`(기본 1초) 간격으로 띄운다, 회차마다 루프 지연을 재서 250ms를 넘으면 경고한다.
- **실행**: `onair-scenario config/scenarios/flood.yaml --llm dummy --minutes 6`, 동시 4·30·60회를 한꺼번에. 수정 뒤에는 30분 방송으로 동시 4회와 60회를 다시 돌렸다.
- **결과** (6분 방송, 회차 평균):

  | 조건 | 동시 실행 | 루프 지연 P95 | 세그먼트 생성 P95 |
  |---|---|---|---|
  | 수정 전 (간격 없음) | 4 / 60 | 재지 않음 | 11.5초 / 23.5초 |
  | 간격만 둠 | 4 / 30 / 60 | 74ms / 1714ms / 2057ms | 11.5초 / 13.7초 / 13.8초 |
  | 간격 + 동기화 끔 | 4 / 30 / 60 | 16ms / 37ms / 60ms | 11.5초 / 11.2초 / 11.4초 |

  수정 뒤 동시 4회와 60회(실행 `var/lag-4`, `var/lag-60`)를 같은 seed 4쌍으로 견주면 세그먼트 생성 P95는 11.45초와 11.41초, 반영 시간 중앙값은 27.6초와 28.0초로 모든 지표가 차이 없음이다.

  30분 방송 검증(실행 `var/par-low/20261110-121446`과 `var/par-high/20261110-121446`, 동시 4회와 60회): 루프 지연 P95는 동시 4회 31ms, 동시 60회 회차 평균 179ms(가장 큰 회차 203ms)였다. 같은 seed 4쌍의 세그먼트 생성 P95는 12.21초와 12.22초로 같았고 다른 지표도 모두 차이 없음이다.
- **판정**: 채택. 동시 60회에서 타이밍 지표가 틀어지지 않았다. 다만 flood 60회의 루프 지연이 경고 기준(250ms)에 가까우므로 입력이 많은 시나리오는 60회를 넘기지 않는다.
- **남은 것**
  - 수정 전과 "간격만 둠"의 원자료는 남기지 않았다(도구를 만들던 중의 측정이다).
  - 60회를 넘는 동시 실행과 실제 LLM을 쓰는 동시 실행은 재지 않았다. 경고가 뜨는지로 판단한다.
  - 30분 방송에서는 같은 seed라도 두 실행의 경로가 갈렸다. 생성 수가 32 ± 4.8과 31.5 ± 2.4, 반영 시간 중앙값이 216 ± 213초와 122 ± 185초였다. 동시 실행 수가 달라서인지, 실시간 실행이 원래 그런지는 이 실행으로 가를 수 없다 — T-002에서 잰다.

### T-002 실행기: 값이 같은 변형과 견주면 차이 없음이 나오는가 (2026-11-10) — 채택

- **증상**: T-001의 30분 검증에서 같은 seed의 두 실행이 서로 다른 경로를 갔다. 짝 비교가 흔들림을 실제로 줄이는지, 아무것도 바꾸지 않았는데 개선·악화로 판정하지는 않는지 확인이 필요했다.
- **원인 층**: 도구.
- **가설**: 지금 값과 같은 값을 변형으로 주면 모든 지표가 차이 없음으로 나오고, 짝 차이의 흔들림은 짝 없이 견줄 때보다 작다.
- **목표 지표**: 개선·악화 판정 수(5% 기준이므로 29개 중 한두 개는 우연히 나올 수 있다), 짝 차이의 표준편차를 짝 없이 견줄 때의 표준편차로 나눈 값.
- **변경**: 없음 (검증).
- **실행**: `onair-scenario config/scenarios/sparse.yaml config/scenarios/flood.yaml --llm dummy --sweep flood_threshold=8 --repeat 10 --parallel 40` — `flood_threshold`의 지금 값이 8이다. 실행 `var/aa/20261110-124344`, 30분 방송, 루프 지연 P95는 가장 큰 회차가 32ms.
- **결과**: 방향이 있는 지표 29개(두 시나리오 합) 가운데 개선·악화 판정은 0개다. 아래는 짝 차이의 표준편차를 짝 없이 견줄 때의 표준편차로 나눈 값이다. 1보다 작을수록 짝짓기가 흔들림을 줄였다.

  | 지표 | flood | sparse |
  |---|---|---|
  | 세그먼트 생성 P95 | 0.09 | 0.28 |
  | 생성 수 | 0.23 | 0.61 |
  | 반영 시간 중앙값 | 0.46 | 0.68 |
  | 문자 반영률 | 모든 회차 1 | 0.68 |
  | 같은 첫머리 | 0.62 | 0.89 |

- **판정**: 채택. 짝 비교는 어느 지표에서도 손해가 아니다. 타이밍 지표의 흔들림은 1/4~1/11로 줄이고, 반영 지표는 1/1.5~1/2로 줄인다. 같은 seed라도 실시간 실행에서는 작은 시차가 다른 선별로 이어져 경로가 갈리기 때문이다.
- **남은 것**
  - 아무것도 바꾸지 않았는데 sparse의 문자 반영률 평균이 0.70과 0.85로 달랐다(판정은 차이 없음). 반영 지표로 판정하려면 10회로도 모자랄 수 있다 — 회차 수는 `onair-compare <폴더>`의 "구분되는 차이"로 정한다.
  - 실제 LLM에서는 대본까지 달라지므로 짝짓기 효과가 이보다 작을 것으로 본다. 재지 않았다.
