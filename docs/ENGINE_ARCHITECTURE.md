## 1. 범위와 책임

기획서 9장(역할 분담) 기준, 대본 엔진의 책임은 다음과 같다.

| 책임 | 관련 요구사항 |
|---|---|
| 코너 편성표 정의 및 순환 진행 (편성 관리자) | F-01 |
| 코너별 프롬프트 기반 대본 생성 (LLM 오케스트레이션) | F-02 |

| 세그먼트 메타데이터 생성 (제출 페이로드) | 9장 인터페이스 계약 |

**엔진이 하지 않는 것** — 방송 클럭, 믹싱/크로스페이드, HLS 서빙, 언더런 방어의 최종 책임(폴백 재생 실행), 요청의 최초 수신 라우팅, **곡 선정과 YouTube 재생**(F-34)은 스트리밍 백엔드 담당이다. 엔진은 오디오+메타데이터를 **제출**하는 생산자이고, 백엔드가 방송 시간축의 소유자다.

**상태 머신에서의 담당 구간** — 5.4절 상태 머신 중 엔진은 `SCREENED → QUEUED → GENERATING → GENERATED` 구간을 소유한다. `REQUESTED`(수신)와 `MIXING` 이후는 백엔드 소유. `REJECTED` 판정은 L0~L2 어느 계층에서든 엔진이 내리고 백엔드에 통보한다.

## 2. 설계 원칙

1. **미정 사항은 인터페이스 뒤로** — 코너 구성(4.2 미정)은 `Corner` 인터페이스 뒤에, 편성 정책(8장 미정)은 `SchedulingPolicy` 인터페이스 뒤에 둔다. 확정되면 구현체만 추가하고 엔진 본체는 수정하지 않는다.
2. **파이프라인은 단계(stage)로 분해** — 프롬프트 구성 → LLM → L2 검사 → TTS → 패키징을 독립 단계로 나누고, LLM/TTS 제공자는 어댑터로 격리해 교체 가능하게 한다.
3. **관통 우선, 품질은 교체** — 모든 단계는 처음부터 더미 구현(하드코딩 대본, 미리 만든 오디오)을 갖는다. 실제 구현은 더미를 하나씩 교체하는 방식으로 들어간다.
4. **계측은 처음부터** — 상태 전이 타임스탬프와 생성 지연 기록은 실험 데이터(RQ1~RQ3)의 원천이므로, 나중에 붙이는 부가 기능이 아니라 파이프라인의 기본 동작으로 넣는다.
5. **되돌릴 수 없는 경계 이전에 안전 검사 완료** — L0~L2는 전부 엔진 내부, 즉 세그먼트 제출 이전에 끝난다. 제출된 오디오에는 부적절 콘텐츠가 없다는 것이 엔진이 백엔드에 제공하는 계약이다.

## 3. 전체 구조

```
                        ┌────────────────────────────────────────────────┐
                        │                 Station Engine                  │
                        │              (스테이션당 1 인스턴스)              │
  [RSS/피드] ──수집──→  │  ┌──────────┐                                  │
                        │  │ 소스 수집기│──소재──┐                         │
                        │  └──────────┘        ▼                         │
  요청 이벤트 ──────→   │  ┌──────────┐   ┌─────────────┐                │
  (백엔드 발행)          │  │ 요청 접수 │──→│  편성 관리자  │← SchedulingPolicy
                        │  │  (L0)    │   │ (Scheduler)  │← RunningOrder  │
                        │  └──────────┘   └──────┬──────┘                │
  백프레셔/상태 통보 ──→ │        ▲               │ "다음 생성 대상"        │
  (백엔드 발행)          │        │               ▼                       │
                        │  ┌─────┴────────────────────────────┐          │
                        │  │        생성 파이프라인              │          │
                        │  │ 프롬프트 구성 → LLM(L1 내장)        │          │
                        │  │   → L2 검사 → TTS → 패키징         │          │
                        │  └──────────────────┬───────────────┘          │
                        │                     │ 오디오 파일 + 메타         │
                        │  ┌────────┐         ▼                          │
                        │  │ 계측 로그│   ┌──────────┐                    │
                        │  │(SQLite) │   │  제출기   │ ──── 제출 ────→ [스트리밍 백엔드]
                        │  └────────┘   └──────────┘                     │
                        └────────────────────────────────────────────────┘
```

- **Station Engine**은 스테이션(방)당 1개 인스턴스로 기동한다(F-25). **다중 스테이션 동시 운영은 검증 필수 범위다**(확인 9 결정). 그림에는 없지만 상위에 **EngineManager**가 있어, 백엔드가 발행하는 방 생성/종료 이벤트(`station.created`/`station.closed`, 5.2절)에 따라 StationEngine 인스턴스를 기동·종료한다. 개발 순서상 M0~M2는 단일 스테이션 고정으로 진행하되, 전역 상태를 두지 않는 원칙으로 다중 전환 비용을 낮춘다.
- 런타임은 **Python + asyncio 단일 프로세스**를 기본으로 하고, 한 프로세스 안에서 EngineManager가 여러 StationEngine을 비동기 태스크로 구동한다. LLM/TTS 호출이 전부 I/O 바운드이므로 검증 목표 규모(소수의 동시 스테이션)에는 단일 프로세스로 충분하며, 프로세스 분리는 그 규모를 넘을 때 검토한다.
- **비용 상한**: 동시 생성 개수 제한을 스테이션별 상한과 **전역 상한** 두 층으로 둔다. 빈 방도 생성 비용을 계속 소비하는 문제(기획서 10장 리스크)에 대한 엔진 쪽 최소 방어선이다.

### 3.1 핵심 제어 흐름

편성 관리자가 유일한 의사결정 지점이다. 루프는 단순하다:

```
loop:
    ctx = 현재 상황 스냅샷 (러닝오더 위치, 대기 요청 큐, GENERATED 잔량, 백프레셔 신호, 최근 생성 지연 통계)
    decision = policy.decide(ctx)          # 다음에 무엇을 생성할지 (코너 진행 / 요청 반영 / 필러)
    if decision.skip: await 이벤트 또는 타이머; continue
    task = 생성 파이프라인.submit(decision) # 비동기 실행, 완료 시 제출기로
```

- LLM은 "무엇을 말할지"를 결정하지 않는다. 편성 관리자가 칸을 정하고 LLM은 칸을 채운다(기획서 5.1의 핵심 설계 유지).
- 파이프라인 실행은 비동기 태스크이므로, 편성 관리자는 생성 완료를 기다리지 않고 다음 판단을 할 수 있다(선생성/버퍼 축적). 동시 생성 개수는 설정으로 제한한다(비용 상한).

## 4. 핵심 컴포넌트

### 4.1 편성 관리자 (Scheduler)

**입력**: RunningOrder(러닝오더), 요청 큐, 백엔드가 통보하는 큐 잔량·백프레셔, 자체 생성 지연 통계.
**출력**: `GenerationJob` (무엇을, 어떤 소재로, 어떤 우선순위로 생성할지).

- **RunningOrder**는 "코너 슬롯의 순서 있는 목록 + 현재 위치"다. 4.2절 코너 구성이 미정이므로, 러닝오더의 **생성 규칙**(방송 시간·DJ 스타일 → 슬롯 배열)은 `RunningOrderBuilder` 인터페이스 뒤에 두고, MVP는 하드코딩된 고정 배열 빌더로 시작한다.
- **재배치 규칙**: 엔진이 소유한 상태(QUEUED, GENERATING, GENERATED)만 재배치·취소할 수 있다. 제출된 세그먼트는 건드리지 않는다. GENERATING 취소는 "LLM/TTS 호출 결과를 버리는 것"으로 구현한다(API 호출 자체의 중단은 시도하지 않음 — 단순함 우선, 비용은 로그로 관찰).

### 4.2 편성 정책 (SchedulingPolicy) — 연구 확장점

8장이 비어 있으므로 지금 정할 수 있는 것은 **인터페이스와 계측 지점**뿐이다.

```python
class SchedulingPolicy(Protocol):
    def decide(self, ctx: ScheduleContext) -> Decision: ...
```

- `ScheduleContext`에는 정책 비교 실험에서 독립·매개 변수가 될 수 있는 값을 전부 담는다: 요청 도착률(최근 창), GENERATED 버퍼 잔량(초), D_total 추정치, 러닝오더 잔여, 요청별 대기 시간.
- `Decision`은 최소한 {다음 생성 대상, 요청 반영 여부, 접수 확인(ack) 송출 여부, 재배치 지시}를 표현한다. **접수 확인의 송출/생략이 Decision의 1급 필드**여야 RQ2(생략된 요청자 관측)가 측정 가능하다.
- MVP 정책은 `NaiveFifoPolicy`(코너 진행 우선, 코너 경계에서 요청을 FIFO로 반영, ack는 항상 송출) 하나로 시작한다. 정책 A/B/C는 8장 확정 후 이 인터페이스의 구현체로 추가한다.
- 정책 전환(F-11)은 스테이션 설정으로 주입한다. 방송 중 핫스왑은 요구사항이 아니므로 구현하지 않는다(실험 조건은 세션 단위로 고정된다고 가정 — **[확인 8]**).
- **코너별 정책** — 코너마다 다른 정책을 쓰는 경우(예: 사연 코너는 A, 참여 코너는 B)도 "코너→정책 대응표" 하나를 세션 단위로 고정하는 것이므로 확인 8과 충돌하지 않는다. 편성 관리자는 현재 코너에 맞는 정책을 대응표에서 골라 `decide`를 부른다. 평가 설계는 [persona.md](persona.md) 8.1절 **[확인 12]**.

### 4.3 코너 (Corner) — 편성 확장점

코너 1개 = "이 칸을 채우는 방법"의 정의:

```python
class Corner(Protocol):
    corner_type: str                  # "opening" | "story_corner" | "music_intro" | ...
    async def gather(self, ctx) -> Material   # 소재 수집 (게시판 사연, 곡 정보, 주제 등)
    def build_prompt(self, material, station_style) -> Prompt   # L1 지시 포함
    expected_duration: range          # 편성 관리자의 시간 계산용
```

**코너 구성 (결정 2026-10-08)** — 방송은 오프닝 → 본 코너 → 엔딩 3단계다. 코너 이름은 **권장 이름**이다(현재 코드에는 MVP 임시 5종만 있다).

| 단계 | 코너 | 소재 | 비고 |
|---|---|---|---|
| **오프닝** | (첫 곡) | 호스트가 지정한 `first_song` | 방송 시작과 함께 **백엔드가 바로 튼다.** 엔진은 그동안 오프닝 멘트를 만든다 — 첫 멘트의 생성 지연을 곡이 가려 준다 |
| | `opening` | 스테이션 컨셉, 방송 설명, 방금 나간 첫 곡 | 인사 + 방송 소개 + 첫 곡 언급 |
| | `topic_intro` | 오늘의 주제(`topic`) | 비어 있으면 방송 시작 시 컨셉에서 한 번 생성 |
| | `corner_preview` | 오늘의 러닝오더 | 오늘 순서 안내 |
| **본 코너** (순환) | `story_corner` | 게시판 사연 (규칙으로 선택) | 사연 읽기 — 미리 쌓인 사연이라 선생성할 수 있다 |
| | `topic_corner` | 오늘의 주제 + 관련 채팅 | 주제 토크 |
| | `participation_corner` | 실시간 채팅 | 청취자 참여형 — 질문 던지기·반응 모으기. 채팅을 즉시 반영하는 정책과 짝을 이룬다 |
| | `music_intro` | 백엔드가 미리 정한 다음 곡(`track.queued`) | 곡 소개 → 바로 곡 재생. 신청곡이면 신청자 언급 (반영 ③단계) |
| | `vote_call` | 선곡 투표 진행 상태 | 마지막 곡 투표 안내. 엔딩 전 1회 이상 |
| **엔딩** | `closing` | 오늘 방송 요약(송출 이력), 투표로 정해진 마지막 곡 | 엔딩 멘트 + 마지막 곡 소개 → 마지막 곡 |
| 공통 | `request_reply` | 청취자 채팅 요청 | 정책이 반영을 결정하면 코너 사이에 끼어든다 |
| | `filler` | 없음/저맥락 | 버퍼 방어용 짧은 멘트 |
| | ack | 사전 렌더 템플릿 | 4.5절 단축 경로 |

**러닝오더와 시간 배분** — `RunningOrderBuilder`가 `broadcast_minutes`(MVP 30~60분)로 슬롯 배열을 만든다. 곡 길이는 `track.queued`의 `duration_ms`를 쓰고, 모르면 4분으로 가정한다. 수치는 모두 `[예시]`다.

| | 30분 방송 | 60분 방송 |
|---|---|---|
| 오프닝 (첫 곡 + `opening`·`topic_intro`·`corner_preview`) | 약 6분 | 약 6분 |
| 본 코너 — [코너 멘트 1~3분 + 곡 소개 + 곡] 반복 | 약 18분, 3회 | 약 46분, 8회 |
| `vote_call` | 종료 15분 전 | 종료 15분 전 |
| 엔딩 (`closing` + 마지막 곡) | 약 6분 | 약 6분 |

- 본 코너 순환 순서 예: `story_corner` → 곡 → `topic_corner` → 곡 → `participation_corner` → 곡 → (반복). 사연 풀이 비면 `story_corner` 대신 다른 코너로 대체한다.
- 방송 길이를 맞추는 것은 **엔딩 시작 시각**이다. 본 코너 순환은 남은 시간이 엔딩 길이에 닿으면 멈추고 엔딩으로 넘어간다. 곡 재생 중에 그 시각이 오면 곡이 끝난 뒤 넘어간다.
- DJ 스타일(F-25)은 코너가 아니라 **스테이션 설정**(persona)이며, 모든 코너의 프롬프트에 공통 주입된다 ([persona.md](persona.md) 4절).

### 4.4 생성 파이프라인

```
GenerationJob
  → [1] 프롬프트 구성   Corner.build_prompt + StationProfile + 직전 방송 맥락 요약
  → [2] LLM 호출        L1: 프롬프트에 "부적합 시 대본 대신 REJECT 출력" 지시 내장
  → [3] L2 출력 검사     생성된 대본 텍스트에 금칙어/정규식 재검사
  → [4] TTS 호출        대본 → 오디오 파일
  → [5] 패키징          duration 실측, 메타데이터 부여 → 제출기로
```

- 각 단계는 인터페이스로 분리하고, LLM/TTS는 provider 어댑터(`LlmClient`, `TtsClient`)로 격리한다. 더미 어댑터(고정 텍스트 반환, 미리 녹음된 wav 반환)를 처음부터 유지해 API 키 없이도 전체 파이프라인을 돌릴 수 있게 한다(테스트·부하 실험·발표장 폴백 겸용).
- **[2]에서 REJECT가 나오면** 해당 Job을 REJECTED로 종결하고 백엔드에 통보한다(요청 유래 Job인 경우 요청자 UI 피드백용, F-15). 코너 진행용 Job이 REJECT되면 filler로 대체한다.
- **실패 처리(MVP 규칙)**: LLM/TTS 호출 실패·타임아웃 시 1회 재시도, 재실패 시 filler 대체. 정교한 재시도 전략은 실측 후 조정한다.
- 모든 단계 경계에서 타임스탬프를 기록한다(→ 7장 계측).
- **[1]의 방송 맥락은 최근 N개 세그먼트의 요약만 유지한다**(확인 10 결정). 방송 간 장기 기억(F-23)은 두지 않는다. N 초깃값은 8로 두고 프롬프트 길이·대본 품질 실측 후 조정한다.

### 4.5 접수 확인(ack)의 단축 경로

L_ack는 실험의 핵심 측정값인데, ack를 매번 LLM+TTS로 생성하면 L_ack가 생성 지연에 지배당한다. 따라서 ack는 **본 파이프라인을 타지 않는 단축 경로**로 처리한다:

- **①단계는 "낭독"이다** (결정 2026-10-08, [persona.md](persona.md) 6절). 접수 확인은 채팅 본문을 소리 내어 읽는다. 그래서 문구 전체를 미리 녹음해 둘 수 없다 — 지금 구현(채팅을 읽지 않는 고정 문구 사전 렌더)은 바꿔야 한다.
- **방식 (제안)** — LLM을 거치지 않는다. 앞뒤 고정 문구("이런 사연이 들어왔어요", "곡 끝나고 이야기 나눠 볼게요" 류)는 방송 시작 전에 그 방 보이스로 **사전 렌더링**해 두고, **채팅 본문만 즉시 TTS**해서 이어 붙인다.
  - 읽는 본문은 L0를 통과한 것만이다. 너무 긴 채팅은 앞부분만 읽는다(예: 60자 `[예시]`).
  - 저지연 TTS(Cartesia, 확인 3)라 본문 합성은 수백 ms 수준이라 즉시성은 대부분 유지된다.
- **측정 해석이 바뀐다** — L_ack에 엔진의 본문 TTS 지연이 들어간다. 그래서 L_ack를 "엔진 TTS 지연"과 "편성·백엔드 경로"로 나눠 기록한다(계측 `generation_log`의 tts 단계). 이전 설계(엔진 기여분 ~0)와 다르다는 점을 실험 보고에 밝힌다.

### 4.6 안전 계층 (F-13)

| 계층 | 엔진 내 위치 | 구현 |
|---|---|---|
| L0 | 요청 접수기 — 요청 이벤트 수신 직후 | 금칙어·정규식(연락처, URL, 욕설, 특정인 지목). 룰은 코드가 아니라 데이터 파일(`safety/rules.yaml`)로 관리 |
| L1 | 프롬프트 구성 단계 | 대본 생성 프롬프트에 판단 지시 내장, 별도 LLM 호출 없음 |
| L2 | TTS 직전 | L0과 동일 룰셋 + LLM 산출물 특화 패턴 재검사 |

- L0 탈락 시 즉시 REJECTED 통보(파이프라인 진입 없음). 안전 계층은 정책과 무관하게 전 실험 조건에서 동일 적용하며, L0·L2 소요 시간을 계측해 보고한다(기획서 5.4의 요구).

### 4.7 소스 수집기 (F-04)

- RSS/피드를 주기 폴링해 로컬 캐시(SQLite 또는 JSON 파일)에 적재하는 독립 백그라운드 태스크. 브리핑 코너의 `gather`는 이 캐시만 읽는다 — **생성 경로에서 외부 네트워크를 기다리지 않는다**(지연 예측 가능성 확보).
- 수집 실패는 방송을 막지 않는다: 캐시가 비면 브리핑 코너는 스킵되고 편성 관리자가 다른 코너로 대체한다.

### 4.8 곡 — YouTube 재생 (결정 2026-10-08, F-17·F-34)

- **곡 선정과 재생은 백엔드**가 한다(F-34, YouTube 플레이리스트 서버 재생). 곡 출처는 플레이리스트, 청취자 신청곡(YouTube 링크), 호스트가 지정한 첫 곡, 투표로 정한 마지막 곡이다.
- **엔진은 곡을 고르지 않는다.** 백엔드가 다음 곡을 미리 정해 `track.queued`(제목·아티스트·길이)로 알려주면, 러닝오더가 음악 칸에 왔을 때 그 곡의 소개 멘트를 만들어 `music_ref`로 지정한다. **어떤 곡은 백엔드, 언제는 엔진**이다 ([ENGINE_REDIS_CONTRACT.md](ENGINE_REDIS_CONTRACT.md) 3.4절).
- **곡 시간** — 엔진은 `track.started`의 시작 시각과 `duration_ms`로 곡이 끝나는 시각을 안다. 편성 관리자의 버퍼 계산(`Scheduler`의 `generated_buffer_sec`)은 지금 멘트 오디오 길이만 세므로, 곡 재생 시간을 더하도록 고쳐야 한다(구현 항목). 그렇지 않으면 곡이 나가는 동안 멘트가 바닥난다고 착각해 필요 이상으로 생성한다.
- **신청곡** — 전용 폼(곡 제목·아티스트·링크·한마디)으로 받고, 링크가 없으면 백엔드가 YouTube 검색 결과 중 청취자가 고르게 한다. 백엔드가 곡 정보로 풀어 `request.arrived`(`kind: "song"`)의 `track`에, 한마디는 `body`에 싣는다 ([ENGINE_REDIS_CONTRACT.md](ENGINE_REDIS_CONTRACT.md) 3.4절).
- **BGM과 더킹** (결정 2026-10-08) — MVP는 멘트 밑에 별도 BGM을 깔고 DJ가 말할 때만 줄이는 방식만 한다. 곡과 멘트는 겹치지 않으므로 엔진 변경은 없고, 믹싱은 백엔드가 한다. 실제 곡 위에 겹쳐 말하기(talk-over)는 MVP 이후로 미룬다 ([ENGINE_REDIS_CONTRACT.md](ENGINE_REDIS_CONTRACT.md) 3.6절, **[확인 14]**).
- **무드 신청**(F-17) — 유지 여부는 기획서에서 검토 중이다. 유지한다면 엔진은 무드에 대한 리액션 멘트만 만들고, 무드에 맞는 곡 선정은 백엔드가 한다.
- **카탈로그(`catalog.py`)는 로컬 개발·테스트용 더미로만 남긴다.** 무드 태그 매칭·라이선스 필드·카탈로그 조회 REST는 만들지 않는다 (확인 5 무효).
- 곡 제목·아티스트는 외부 텍스트(YouTube 메타데이터)이므로 프롬프트에는 데이터 블록으로만 넣는다.

## 5. 데이터 모델 (초안)

인터페이스 계약(기획서 9장)의 엔진 쪽 구체화. **1주차 계약 확정 회의에서 백엔드 파트와 합의 후 고정한다.**

### 5.1 세그먼트 제출 페이로드 (엔진 → 백엔드)

```json
{
  "id": "seg_01J9XK...",           // 엔진 발급 ULID
  "station_id": "st_001",
  "audio_ref": "audio/st_001/seg_01J9XK.mp3",  // 공유 스토리지 상대 경로 — [확인 1]
  "duration_ms": 12400,             // 실측값
  "corner_type": "request_reply",
  "kind": "speech",                 // speech | music | ack | filler
  "priority": 50,
  "reorderable": true,
  "request_ref": "req_abc123",      // 요청 유래가 아니면 null
  "music_ref": "yt:dQw4w9WgXcQ",     // 이 멘트 바로 다음에 틀 곡 — 백엔드가 track.queued로 알려준 track_ref (4.8절)
  "created_at": 1789496813.26       // Unix 초 (계약 결정 2026-10-08)
}
```

### 5.2 백엔드 → 엔진 이벤트

| 이벤트 | 페이로드 요지 | 엔진의 반응 |
|---|---|---|
| `request.arrived` | 요청 id, 유형(사연/무드/신청곡), 본문, 요청자 ref, 신청곡이면 곡 정보 | L0 검사 → 요청 큐 적재(SCREENED) 또는 REJECTED 통보 |
| `backpressure` | D_total 현재값, 임계값, 심각도 | 정책 컨텍스트에 반영 → filler 우선 생성 / 요청 반영 보류 |
| `state.transition` | 세그먼트 id, 새 상태(MIXING/PUBLISHED/PLAYED), 시각 | 재배치 가능 집합에서 제거, 계측 기록, 방송 맥락 갱신 |
| `station.created` | 방송 시간, 첫 곡, 오늘의 주제, persona 본문, 정책 | EngineManager가 StationEngine 기동, ack 캐시 사전 렌더링 → `station.started`/`station.rejected` |
| `track.queued` / `track.started` | 다음에 틀 곡 정보 / 곡 재생 시작 시각 | 곡 소개 멘트 생성 / 곡 종료 시각을 버퍼 계산에 반영 (4.8절) |
| `board.story` | 게시판 사연 | L0 검사 → 사연 풀 적재, `story_corner`가 규칙으로 선택 |
| `station.closed` | 스테이션 id, 사유(정상 종료/운영자 중단) | 진행 중 생성 취소, 인스턴스 종료, 계측 플러시 |

### 5.3 엔진 → 백엔드 통보 (제출 외)

| 통보 | 용도 |
|---|---|
| `request.state` (SCREENED/QUEUED/GENERATING/GENERATED/REJECTED) | 요청 상태 머신의 엔진 구간 전이. 프론트의 요청자 피드백(F-15)의 원천 |
| `engine.health` (주기 하트비트: 버퍼 잔량 초, 진행 중 생성 수, 최근 지연 P95) | 운영자 콘솔(F-14)·백엔드 감시용 |

## 6. 백엔드와의 통신·배포 형태 (결정 — [확인 1])

기획서의 기술 스택 장은 rev.8에서 별도 문서로 이관되었다(문서 작성 예정). 백엔드가 큐·방송 상태 관리에 Redis를 사용하는 구상은 유지되고 있으므로 아래를 기본안으로 제안하되, 기술 스택 문서가 확정되면 그에 맞춰 갱신한다.

- **이벤트(양방향)**: Redis Streams (스테이션별 스트림 `engine:{station_id}:in` / `:out`). pub/sub 대비 재기동 시 유실이 없어 상태 머신 통보에 안전하다.
- **오디오 전달**: 단일 머신 배포 전제(발표장 로컬 서버 시나리오와 일치)로 **공유 파일 시스템 경로**를 페이로드에 담는다. 오브젝트 스토리지 도입은 하지 않는다.
- **세그먼트 제출**: 이벤트와 동일하게 Redis Stream으로 (파일 먼저 쓰고 메시지 발행).

HTTP API 방식(백엔드 FastAPI에 POST)도 가능하나, 백엔드→엔진 방향의 이벤트 푸시가 어쨌든 필요하므로 채널을 Redis 하나로 통일하는 편이 단순하다. **1주차 계약 회의의 결정 사항.**

> **결정 (2026-09-20)**: 위 제안대로 **흐름은 Redis Streams**, **오디오는 공유 파일시스템 경로**로 한다. 운영자 콘솔용 관측도 5.3의 `engine.health` 하트비트를 그대로 쓴다 — 버퍼 잔량·진행 중 생성 수·지연 P95에 러닝오더 위치, 정책 이름, 직전 주기의 결정 요약을 더해 발행한다.
>
> 다만 **푸시로 감당이 안 되는 조회 5개**(`/health`, 전역 상태, 결정 로그, 곡 카탈로그 2개)는 엔진이 GET 전용 REST로 연다. *(2026-10-08 갱신: 곡 카탈로그 2개는 YouTube 전환으로 없앴고, 방 생성 화면용 persona 초안 생성 POST 2개를 추가했다 — 계약 6장.)* 결정 로그는 실측 초당 1.2~2.1건이라 스트림에 실으면 세그먼트 보존 구간을 깎아먹고, `ScheduleContext` 스키마가 실험 중 계속 바뀌어 계약에 묶기 어렵다. 곡 카탈로그는 정적 데이터라 푸시 대상이 아니다. 엔진이 포트를 여는 범위는 여기까지이며, 생산자 역할 자체는 그대로다.
>
> 스트림·envelope·전달 보장·오디오 파일 규칙, 하트비트 페이로드, 조회 REST 목록, 백엔드 파트 API 표와의 매핑은 [ENGINE_REDIS_CONTRACT.md](ENGINE_REDIS_CONTRACT.md)에 정리했다 (2026-10-08 미결 사항 확정 — 흐름은 엔진 구현 완료, 하트비트·REST·신규 이벤트는 미구현).

## 7. 계측 (실험 데이터의 원천)

- 엔진 로컬 SQLite(`engine_metrics.sqlite`)에 기록. 테이블 초안:
  - `generation_log`: job id, corner_type, request_ref, 각 파이프라인 단계의 시작/종료 시각, 토큰 수, 결과(ok/reject/fail)
  - `request_log`: 요청 id, 상태 전이 시각 전부(L_ack·L_res 계산 및 RQ2의 (a)/(b) 집단 분류의 원천)
  - `decision_log`: 정책 결정 스냅샷(ScheduleContext 요약 + Decision) — 정책 비교 실험의 핵심 데이터. **결정하지 않은 것(ack 생략 등)도 기록한다.**
- 백엔드·프론트 계측과의 조인 키는 `segment_id`/`request_id`. 시계는 서버 시각 기준(엔진·백엔드 동일 머신 전제면 문제없음).

## 9. 단계별 구현 계획

기획서의 개발 일정 장은 rev.8에서 삭제되어 별도 일정 문서로 관리될 예정이다. 따라서 여기서는 **주차를 못 박지 않고 단계의 순서·내용·완료 기준만** 정의한다. 단계 전환은 날짜가 아니라 완료 기준 충족으로 판단하며, 별도 일정 문서가 확정되면 M0~M4를 그 일정에 매핑한다([확인 11]).

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| **M0 관통** | transport + 제출기 + 더미 파이프라인(하드코딩 대본, 미리 만든 오디오 3~4개 순환 제출) | 백엔드가 엔진 제출물을 받아 프론트에서 소리가 남. 계약 스키마 v1 고정 |
| **M1 생성 v1** | LLM/TTS 실어댑터, 코너 3종(opening·music_intro·filler), 고정 러닝오더, L1/L2, 계측 기본 | 실생성 대본으로 30분 무개입 방송. 생성 지연 분포 첫 실측 리포트 |
| **M2 버퍼·안정성** | 선생성 버퍼 관리, 백프레셔 반응, briefing 코너+RSS, 실패 처리·filler 대체 | 3시간 무중단 (백엔드 통합 기준). D_total 임계 실측치 산출 |
| **M3 요청 반영·다중 스테이션** | request.arrived 처리, L0, request_reply 코너, ack 단축 경로, F-15 통보. EngineManager(station.created/closed 수명주기) | 요청 → ack → 본 답변 종단 데모. L_ack/L_res 첫 실측. **스테이션 2개 이상 동시 방송 확인** |
| **M4 정책·실험** | 정책 A/B/C 구현(8장 확정 반영), decision_log 완성, 부하 생성기(F-18) 연동 훅 | 정책 교체가 설정 1줄로 가능. 시스템 실험 자동 스윕에 필요한 입출력 완비 |

각 단계는 이전 단계의 더미/임시 구현을 교체하는 방식이며, 인터페이스(2장 원칙 1)는 M0에서 정한 것을 유지한다.
