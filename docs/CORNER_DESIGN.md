# 코너 편성 · 청취자 입력 반영 설계

**대상**: `apps/engine`의 편성(코너·러닝오더)과 청취자 입력 처리 전체
**상태**: v0.3 (2026-10-12) — **팀 합의 완료.** 관련 문서를 이 문서 기준으로 개정했다(13.1절). 엔진 쪽 미정 사항 결정은 14.1절, 연구 설계(10절)는 확정 전
**대체하는 것**: [ENGINE_ARCHITECTURE.md](ENGINE_ARCHITECTURE.md) 4.1~4.3·4.5절, [PROJECT_PLAN.md](PROJECT_PLAN.md) 4.2·4.3(코너 부분)·5.4(요청 상태 머신)·7.1(지연 정의)·8장, [persona.md](persona.md) 2.2절과 `BehaviorSpec`. 각 문서는 2026-10-12에 이 문서 기준으로 개정했다(13.1절). 계약 변경은 백엔드 합의 전이라 [ENGINE_REDIS_CONTRACT.md](ENGINE_REDIS_CONTRACT.md) 10장에 제안으로만 두었다.

- 표기: `[예시]` = 합의 전 예시값, `[미정]` = 결정되지 않은 선택, **권장 이름** = 코드에 아직 없는 이름
- 이 문서는 기존 설계를 고치는 것이 아니라 **처음부터 다시 세운 것**이다. 기존 이름(러닝오더, SchedulingPolicy, ack, `request.state` 값)은 13절의 대응표로만 연결한다.

## 1. 결정 사항 (2026-10-12)

| # | 결정 |
|---|---|
| D1 | MVP 방송 형식은 **음악 · 사연토크 · 뉴스 3종**이다. 인포테인먼트는 범위에서 뺀다 |
| D2 | 기존 연구 설계(RQ1~3, 정책 A/B/C)는 **잠정 폐기**하고, 새 코너 구조에 맞춰 다시 세운다(10절) |
| D3 | 뉴스 형식은 **채팅을 방송에 반영하지 않는다.** 나중에 몰아서 읽는 회수 코너도 두지 않는다 |
| D4 | 호스트 커스터마이즈는 **프리셋 안에서 선택**하는 방식이다. 반영 모드는 코너에 고정되고, 호스트는 코너 선택과 참여 강도만 고른다(8절) |
| D5 | 요청별 방송 ack(접수 확인 멘트)를 **폐지**한다. 접수 피드백은 UI로, 방송에서의 인정은 집계 단위로 옮긴다(9절) |

### 1.1 왜 갈아엎는가

지금 구조는 고정 러닝오더 1개(`opening → briefing → music_intro → filler` 순환)와 전역 정책 1개(`NaiveFifoPolicy`)로 되어 있다. 정책은 "지금 코너를 진행할지, 요청을 끼워 넣을지"를 코너와 무관하게 FIFO로 정한다. 그 결과:

- 방송 형식·코너마다 청취자 입력을 다르게 다룰 자리가 없다. 뉴스 브리핑 도중에도 사연 답변이 끼어든다.
- 채팅의 반영 형태가 "접수 ack → 본 답변" 하나뿐이다. 실제 라디오의 반영 형태(2절)와 다르다.
- 실험 조작 변수(ack 정책)가 실제 방송에 없는 행동을 전제로 한다.

## 2. 참고: 실제 방송 사례

국내 FM 사연토크 프로그램 1회분(약 45분)을 훑어보고 설계에 참고할 만한 패턴만 추렸다. 사례 하나일 뿐이므로 그 구성을 그대로 따르지 않고, 일반적인 라디오 관행과 겹치는 부분만 가져온다.

### 2.1 구성 (요약)

오프닝(인사·근황·코너 예고·참여 방법 안내) → 짧은 문자 소개 코너 → 본 코너(규칙 설명 → 사연·토론 항목 반복) → 마무리. 1부/2부는 징글로 나뉜다. 청취자 입력은 구간마다 다른 방식으로 들어온다.

### 2.2 설계에 쓴 관찰

1. **채팅은 주로 짧은 인용으로 반영된다.** 이름 없이 거의 원문 그대로, 때로 두어 건을 묶어 말한다. 고르는 기준은 도착 순서보다 **지금 화제와의 관련성**이다. → 5.1절 QUOTE
2. **방송 중 접수 확인(ack)이 없다.** 인용 자체가 반영이다. → 9절
3. **채팅이 대화 방향을 바꾸기도 한다.** 인용한 채팅이 다음 화제가 되는 경우가 신청곡 반영보다 잦다. → 5.2절 STEER
4. **입력마다 공개 정도가 다르다.** 채팅은 익명 인용, 문자는 이름과 함께 낭독, 사연은 이름과 함께 깊게 다룬다. → 4.1절
5. **코너는 항목 루프를 가진 작은 상태 머신이다.** `규칙 설명 → [항목] ×N → 결과` 형태. → 7절
6. **접착 요소는 거의 고정 문구다.** 코너 콜, 마무리 멘트, 징글. → 7.10절
7. **오프닝에서 참여 방법을 안내한다.** 코너별 입력 계약은 청취자에게도 공개되어야 한다. → 7.1절, 12절 `corner.changed`
8. **AI 혼자서는 어려운 것**: 게스트와의 대화, DJ의 실제 근황. 게스트가 필요한 게임형 코너는 **청취자 투표**로 상대를 바꾸면 혼자서도 성립한다. → 7.6절

## 3. 구조: 형식 → 클락 → 코너

```
StationFormat  형식      어떤 코너 풀을, 어떤 비중·제약으로 쓰는가        (config/formats/*.yaml)
   └ Clock     클락      방송 시간 → 코너 배치. 형식별 "1회분 순환 틀"을 늘이고 줄인다
       └ Corner  코너    진행 단계(상태 머신) + 청취자 입력 계약 + 제약
           └ Step  단계  세그먼트 1개를 만드는 단위 (멘트 15~45초 또는 곡)
```

- **형식**은 호스트가 방을 만들 때 고른다. DJ persona(말투)와는 독립이다 — 같은 DJ가 음악 방송도, 사연 방송도 할 수 있다.
- **클락**은 실제 라디오 편성의 포맷 클락(아워 클락) 개념이다. 형식마다 1회분 순환 틀을 정의하고, `ClockBuilder`(권장 이름)가 방송 시간에 맞춰 오프닝 + 순환 ×N + 엔딩으로 펼친다.
- **코너**는 이 문서의 중심이다. 코너가 청취자 입력을 어떻게 다룰지를 **스스로 선언**하고(입력 계약), 편성 관리자는 그 선언을 결정적으로 집행한다. LLM은 고르지 않고, 고른 것을 말로 엮기만 한다.

### 3.1 원칙

1. **고르는 것은 규칙, 말하는 것은 LLM.** 무엇을 인용·낭독할지, 언제 화제를 바꿀지는 편성 관리자가 결정적으로 정하고 로그를 남긴다. 프롬프트로 "적당히 골라서 읽어라"라고 지시하지 않는다(기존 persona.md 1.1의 원칙 유지).
2. **반영 모드는 코너의 속성이다.** 호스트도, 실험 조건도 코너의 반영 모드를 바꾸지 않는다. 실험이 바꾸는 것은 모드 안의 손잡이(선별 기준, 창 길이 등)다.
3. **방송에서의 인정은 집계 단위로, 개인 피드백은 UI로.** 특정 개인을 위해 공유 방송 시간을 쓰는 것은 실제로 반영할 때뿐이다.
4. **되돌릴 수 없는 경계는 유지한다.** 제출된 세그먼트는 회수하지 않는다. 안전 계층 L0~L2는 모든 형식·코너에서 동일하다.

## 4. 청취자 입력 모델

### 4.1 입력 종류

| 종류 (권장 이름) | 보내는 곳 | 성격 | 방송에서 부르는 이름 |
|---|---|---|---|
| `chat` | 플레이어 채팅창 | 짧은 실시간 반응, 휘발성 | 부르지 않음 ("~하신 분") |
| `message` | 플레이어 "사연 보내기" 폼 | 짧은 실시간 사연·근황·응원 (≤200자 `[예시]`) | 닉네임 |
| `board_story` | 전체 게시판 (방송 전·중) | 긴 사연, 주제 태그 | 닉네임 |
| `song_request` | 신청곡 폼 | 곡 + 한마디 | 닉네임 |
| `vote` | 투표 UI (열려 있을 때만) | 선택지 하나 | 부르지 않음 (집계만) |

- 기존 `kind: story | mood | song`에서 `story`는 `message`로, `mood`는 폐지한다(무드 신청은 기획서에서도 유지 여부 검토 중이었다).
- `chat`과 `message`를 나누는 이유: 실제 방송에서 채팅(익명 인용)과 문자(실명 낭독)는 공개 정도와 반영 형태가 다르다(2.2절 4). 청취자에게도 "가볍게 말 걸기"와 "읽어 주길 바라는 사연"을 고를 수 있게 한다.

### 4.2 반영 모드

| 모드 | 동작 | 방송 노출 | 근거 |
|---|---|---|---|
| **QUOTE** | 입력을 풀에 쌓고, 다음 토크 세그먼트를 만들 때 **현재 화제와 관련 있는 최근 입력 0~2건**을 골라 소재로 넣는다. 고르지 않은 입력은 창이 지나면 만료 | 익명 인용 | 2.2절 1 |
| **STEER** | QUOTE로 고른 입력이 화제 전환 조건을 만족하면 다음 단계의 화제로 지정 | 인용 + 화제 전환 | 2.2절 3 |
| **READ** | 받은편지함(inbox)에 모았다가 전용 코너에서 여러 건을 묶어 낭독 | 닉네임 + 낭독 + 리액션 | 2.2절 4 |
| **FEATURE** | 입력이 한 단계(또는 코너)의 **주 소재**가 된다 | 닉네임 + 깊은 반영 | 본 코너 사연, 신청곡 |
| **SOLICIT** | 코너가 질문·투표를 열고, 창이 닫히면 집계해 반영 | 집계 + 대표 인용 | 7.6절 게임 코너 |
| **CLOSED** | 방송에 반영하지 않는다 | 없음 (UI에만 표시) | D3 뉴스 |

STEER는 QUOTE의 확장이므로 STEER를 허용하는 코너는 QUOTE도 허용한다.

### 4.3 입력 계약

코너는 입력 종류별로 모드를 선언한다. 선언하지 않은 입력 종류는 그 코너 동안 **다른 코너로 넘기거나(DEFER) 보류**한다.

```yaml
# 예: 사연토크 형식의 주제 토크 코너
topic_talk:
  contract:
    chat: STEER            # QUOTE + 화제 전환 허용
    message: DEFER         # text_corner의 inbox로
    song_request: DEFER    # 다음 music_intro로
    board_story: none      # 이 코너는 게시판 사연을 쓰지 않음 (풀에 남아 있음)
```

`DEFER`는 반영 모드가 아니라 라우팅 지시다 — "이 입력은 내 것이 아니니 그 모드를 가진 다음 코너의 inbox에 넣어라".

### 4.4 라우팅 (InputRouter, 권장 이름)

```
입력 도착 (backend → engine)
  → L0 검사 ── 실패 → REJECTED
  → 형식 계약 확인 ── 형식이 이 종류를 받지 않음 → NOT_ON_AIR   (예: 뉴스 형식의 chat)
  → 현재 코너 계약 조회
       QUOTE / STEER → QuotePool       → POOLED
       READ          → inbox[READ]      → INBOXED
       FEATURE       → inbox[해당 코너] → INBOXED
       SOLICIT       → 열린 수집 창     → COLLECTED   (창이 없으면 QUOTE와 같게)
       DEFER         → 그 모드를 가진 다음 코너의 inbox → INBOXED
       CLOSED        → 보류 큐          → HELD        (다음 코너 진입 시 재라우팅)
```

- **QuotePool은 코너가 바뀌어도 유지**한다. 다만 창(5.1절 W)이 지나면 만료되므로 앞 코너의 채팅이 오래 남지 않는다.
- **HELD**는 사연토크·음악 형식 안에서 CLOSED 단계(예: 곡 재생 중 브릿지 없음)를 지나는 동안만 쓴다. 뉴스 형식은 형식 단위로 받지 않으므로 HELD가 아니라 NOT_ON_AIR다(D3).

## 5. 반영 모드 상세

### 5.1 QUOTE

**풀**: 입력을 `(input_id, text, arrived_at, requester_ref)`로 쌓는다.

**선별 시점**: QUOTE를 허용하는 코너의 토크 단계가 **세그먼트 생성을 시작할 때** 한 번 고른다(선결합). 지연 결합은 5.1.2절.

**선별 규칙** (권장 이름: `QuoteSelector` — 이것이 실험의 주 손잡이다, 10절)

1. 후보 = 풀에서 `now - arrived_at ≤ W`인 입력. W = 90초 `[예시]`
2. 제외: 직전 인용과 같은 `requester_ref`(연속 금지), 길이 > 60자 `[예시]`(말로 인용하기 어렵다), L2 규칙에 걸리는 텍스트
3. 점수 = 선별 기준에 따라 계산 — 최근성 / 화제 관련성 / 다양성(아직 인용되지 않은 사람 우선) 중 조건별로 정한다(10절)
4. 상위 k건을 고른다. k = 세그먼트당 상한(참여 강도로 정함, 8절)과 "인용 간 최소 간격"(예: 60초 `[예시]`)을 동시에 만족하는 수
5. 고른 입력 → `SELECTED`, 창이 지난 미선택 입력 → `EXPIRED`

**화제 관련성 계산** `[미정]` — 결정적이어야 하고 생성 지연 예산 안에 들어와야 한다.

| 후보 | 장점 | 단점 |
|---|---|---|
| 임베딩 유사도 (현재 화제 요약 ↔ 입력) | 의미 기반, 같은 입력엔 같은 점수 | 임베딩 API 호출 지연·비용, 화제 요약 필요 |
| 키워드 겹침 (형태소 기반) | 지연 거의 0, 외부 호출 없음 | 의미가 같아도 표현이 다르면 놓친다 |
| 배치 LLM 분류 | 정확 | 비결정적, 지연 증가 — 원칙 1과 충돌 |

**결정 (U1)** — 키워드 겹침으로 구현하고, 임베딩은 M6에서 비교 실측만 한다.

**프롬프트에 넣는 방식** — 고른 입력은 데이터 블록으로 넣고(기존 `prompt_data.data_block`, 인젝션 방어 유지), 지시는 "아래 채팅을 '~라고 하신 분이 있네요'처럼 짧게 인용하고 한 문장으로 반응하라. 닉네임이나 ID를 말하지 않는다"로 고정한다. 인용할지 말지를 LLM에 맡기지 않는다 — 넣었으면 반드시 인용한다. 인용이 대본에 실제로 들어갔는지는 생성 후 문자열 대조로 확인하고, 빠졌으면 해당 입력을 `POOLED`로 되돌린다(창이 남아 있을 때).

#### 5.1.1 화제 상태

QUOTE·STEER는 "지금 무슨 얘기 중인가"를 알아야 한다. 코너는 **화제 상태**(권장 이름: `Thread`)를 들고 단계 사이에 넘긴다.

- `topic`: 지금 화제 한 줄 (코너 시작 시 소재에서, STEER 시 입력에서)
- `keywords`: 관련성 계산용 키워드
- `recent_lines`: 직전 1~2개 세그먼트 대본 요약 — 기존 방송 맥락(`recent_segments`)과 별개로, 코너 안에서의 연속성용

#### 5.1.2 지연 결합 `[실험 조건 후보]`

선결합에서는 인용이 재생될 때 입력의 나이가 `대기 시간 + 생성 지연 + 버퍼(약 30초)`가 된다. 버퍼가 클수록 "이미 지나간 얘기를 인용"하게 된다. 지연 결합은 토크 세그먼트와 별도로 **짧은 인용 세그먼트**(5~10초)를 만들어 재생 직전에 끼우는 방식이다.

- 인용 세그먼트는 앞 세그먼트가 끝나는 지점에 자연스럽게 이어져야 하므로 `Thread.recent_lines`를 소재로 쓴다
- 백엔드가 GENERATED 상태 세그먼트 앞에 끼워 넣을 수 있어야 한다(기획서 5.4절 "재배치 가능" 구간). 계약 변경 필요 — 12절
- 버퍼·신선도 실험(10절 RQ-B)의 조작 변수다

### 5.2 STEER

QUOTE로 고른 입력 중 아래를 만족하는 것이 있으면, 다음 단계의 `Thread.topic`을 그 입력으로 바꾼다.

- 코너 계약이 `chat: STEER`
- 입력이 **DJ에게 묻는 질문**이거나 **새 화제 제안**이다 — 판별은 **규칙 기반**(U2 결정) — 물음표, 요청 표현("~해 주세요"), DJ 호칭. 규칙은 데이터 파일로 두고 실제 채팅 로그로 다듬는다
- 코너당 STEER 횟수 상한(참여 강도, 8절) 미만
- 코너의 남은 시간 예산이 한 단계 이상

STEER된 입력은 반영 ③단계(흐름 변경)로 기록한다.

### 5.3 READ

전용 코너(7.4절 `text_corner`)에서 inbox의 `message`를 묶어 낭독한다.

- 한 번에 3~5건 `[예시]`, 건당 낭독 + 1~3문장 리액션
- 선별: 도착 순 + 길이 상한 + 같은 사람 1건 + 다양성(같은 내용 반복 제외) `[예시]`
- 고르지 못한 건은 다음 `text_corner`까지 inbox에 남는다. 방송 종료 시 남은 건은 `EXPIRED`
- 닉네임은 백엔드가 입력에 실어 보낸다(12절). `requester_ref`(내부 ID)는 프롬프트에 넣지 않는다

### 5.4 FEATURE

입력이 단계의 주 소재가 된다.

- `board_story` → `story_corner`(7.5절). 기존 계약 3.5절(사연 풀, `board.story.withdrawn`)을 그대로 쓴다
- `song_request` → `music_intro`(7.3절). 백엔드가 고른 다음 곡이 신청곡이면 신청자 닉네임과 한마디를 소재로 넣는다. 곡을 고르고 트는 것은 백엔드다(기존 결정 유지)

### 5.5 SOLICIT

코너가 수집 창을 연다 → 청취자가 답한다(`vote` 또는 `chat`) → 창이 닫히면 집계를 소재로 반영한다.

- 투표: 엔진이 `vote.open`을 보내고 백엔드가 UI에 띄워 집계, `vote.result`로 돌려준다(12절)
- 질문형(자유 답변): 창이 열린 동안의 `chat`을 `COLLECTED`로 받아, 창이 닫히면 QUOTE 선별 규칙으로 대표 답 2~3건을 고른다
- **창 동안 방송이 비지 않아야 한다.** 창은 곡 재생 또는 다른 단계와 겹치게 연다(7.6절)

### 5.6 CLOSED

방송에 반영하지 않는다. 입력은 버리지 않고 UI에 "지금은 방송에 반영되지 않는 시간"으로 표시한다. 뉴스 형식은 형식 전체가 CLOSED이고 보류·회수도 없다(D3).

## 6. 형식 3종

### 6.1 비교

| | 음악 (`music`) | 사연토크 (`talk`) | 뉴스 (`news`) |
|---|---|---|---|
| 말 : 곡 (시간) | 2 : 8 `[예시]` | 5 : 5 `[예시]` | 7 : 3 `[예시]` (곡은 브릿지) |
| 코너 풀 | 곡 소개, 아티스트·장르 이야기, 신청곡 소개 | 사연, 문자 소개, 주제 토크, DJ 대 청취자 게임 | 헤드라인, 분야별 브리핑, 정리 |
| `chat` | QUOTE (드물게, 곡 사이만) | QUOTE / STEER / SOLICIT | **받지 않음** |
| `message` | 받지 않음 (U4) | READ | 받지 않음 |
| `board_story` | 받지 않음 | FEATURE | 받지 않음 |
| `song_request` | FEATURE (주력) | FEATURE | 받지 않음 |
| `vote` | 엔딩 곡 투표 | 게임 코너, 엔딩 곡 투표 | 없음 |
| BGM | 없음 (곡이 주인공) | 잔잔한 깔림음 | 뉴스 베드음 |
| DJ 주관 | 허용 | 허용 | **금지** (6.4절) |

### 6.2 클락 (1회분 순환 틀) `[예시]`

```
music:  [music_intro → 곡] → [music_intro → 곡] → [artist_talk → 곡] → (반복)
talk:   [본 코너 A] → [music_intro → 곡] → [text_corner] → [music_intro → 곡] → [본 코너 B] → [music_intro → 곡] → (반복)
news:   [headline] → [section ×2~3, 섹션 사이 브릿지 곡 짧게] → [recap] → [곡] → (반복)
```

- 본 코너 A/B는 호스트가 고른 코너를 번갈아 배치한다(8절)
- 방송 길이를 맞추는 기준은 기존과 같이 **엔딩 시작 시각**이다. 남은 시간이 엔딩 길이에 닿으면 순환을 멈추고 엔딩으로 간다. 곡 재생 중이면 곡이 끝난 뒤 넘어간다
- 30분 방송 기준 talk 순환은 약 1.5회, 60분은 약 3.5회 `[예시]` — 실측한 단계 길이로 다시 계산한다

### 6.3 공통: 오프닝·엔딩

모든 형식이 같은 뼈대를 쓰고 내용만 형식별로 다르다.

- **오프닝**: 첫 곡(호스트 지정, 백엔드가 방송 시작과 함께 재생) → `opening`(7.1절)
- **엔딩**: `closing`(7.2절) → 마지막 곡. 마지막 곡 투표(SOLICIT)는 음악·사연토크만, 종료 15분 전 안내 `[예시]`

### 6.4 뉴스 형식의 "주관 금지"

프롬프트 지시만으로는 결정적으로 지킬 수 없으므로 세 겹으로 건다.

1. **소재 제한**: 브리핑 단계의 프롬프트는 수집 소재(RSS 등)만 근거로 쓰고 출처 매체를 밝히도록 지시한다(기존 `briefing` 코너 방식 유지)
2. **L2 규칙 추가**: 뉴스 형식의 대본에만 적용하는 출력단 규칙 — 평가어("다행히", "안타깝게도", "충격적인"), 추측·전망 표현("~할 것으로 보인다"를 출처 없이), 1인칭 의견("제 생각엔")을 검출하면 재생성 1회, 또 걸리면 소재 문장 요약 템플릿으로 대체 `[미정: 규칙 목록]`
3. **persona 표현 층 제한**: 뉴스 형식에서는 persona의 유머·입버릇을 끈다. 말투(존댓말·에너지)만 쓴다

뉴스 형식은 청취자 입력을 받지 않으므로(D3) 시사 토론·청취자 의견 소개 코너는 MVP에 두지 않는다.

## 7. 코너 명세

각 코너는 **입력 · 진행 규칙(단계) · 출력 · 전환 조건 · 계약**을 가진다(기획서 4.3절의 4요소 + 계약).

### 7.0 코너 인터페이스 (권장 이름)

```python
class CornerSpec:                       # config/formats/*.yaml에서 로드
    corner_type: str
    steps: list[StepSpec]               # 진행 규칙 — 항목 루프는 StepSpec.repeat로 표현
    contract: dict[InputKind, Mode]     # 4.3절
    constraints: Constraints            # 예: subjectivity=none, source_required
    budget_sec: tuple[int, int]         # 클락이 배정하는 시간 범위
    exit: ExitRule                      # 전환 조건

class CornerRun:                        # 방송 중 코너 1회 진행의 상태
    spec: CornerSpec
    step_index: int
    items: list                         # 이 코너가 소비할 항목 (사연, 문자, 투표 주제 …)
    thread: Thread                      # 5.1.1절 화제 상태
    state: dict                         # 코너 고유 상태 (예: 게임 점수)
    started_at: float
    def next_job(self, ctx) -> GenerationJob | None   # None = 코너 종료
```

### 7.1 `opening` (공통)

| 요소 | 내용 |
|---|---|
| 입력 | 스테이션 컨셉, 첫 곡, 날짜·시각, 오늘의 주제(없으면 엔진이 생성), 오늘 클락, 형식의 참여 방법 |
| 단계 | ① 인사 + 첫 곡 백어나운스 → ② 오늘의 이야기(주제 소개) → ③ 코너 예고 + **참여 방법 안내** |
| 출력 | 멘트 3개 |
| 전환 | 3단계 완료 |
| 계약 | `chat: QUOTE`(③ 이후만, 뉴스 제외), 나머지 DEFER |

참여 방법 안내는 형식·호스트 선택으로 정해진 계약에서 결정적으로 만든다(예: "사연은 사연 보내기로, 채팅은 언제든지요"). 뉴스는 "이 방송은 청취자 의견을 반영하지 않습니다"를 방송에서 안내하지 않고, UI가 `corner.changed`의 계약 요약으로 표시한다(U7 결정).

### 7.2 `closing` (공통)

| 요소 | 내용 |
|---|---|
| 입력 | 오늘 송출 이력 요약, 게임 결과(있으면), 마지막 곡(투표 결과 또는 백엔드 선택) |
| 단계 | ① 오늘 방송 돌아보기(반영된 사연·채팅 1~2건 회상 — 반영 ④단계) → ② 마지막 곡 소개 + 끝인사 |
| 전환 | 마지막 곡 종료 = 방송 종료 |
| 계약 | `chat: QUOTE`(음악·사연토크), 나머지 CLOSED |

### 7.3 `music_intro` (음악·사연토크·뉴스 브릿지)

| 요소 | 내용 |
|---|---|
| 입력 | 백엔드가 미리 정한 다음 곡(`track.queued`), 신청곡이면 신청자 닉네임·한마디 |
| 단계 | ① 곡 소개 (신청곡이면 FEATURE 반영) → 곡 재생(백엔드) |
| 전환 | 곡 종료 |
| 계약 | `song_request: FEATURE`, `chat: QUOTE`(곡 소개 멘트에 0~1건, 음악·사연토크만), 곡 재생 중은 CLOSED → HELD |

### 7.4 `text_corner` — 문자 소개 (사연토크)

| 요소 | 내용 |
|---|---|
| 입력 | `message` inbox |
| 단계 | ① 코너 콜(고정 문구) → ② [문자 낭독 + 리액션] ×3~5 → ③ 마무리(고정 문구) |
| 전환 | 항목 소진 또는 예산 초과. inbox가 2건 미만이면 이번 차례를 **건너뛰고** 다음 코너로 `[예시]` |
| 계약 | `message: READ`, `chat: QUOTE`(낭독 사이 리액션에 0~1건), 나머지 DEFER |

### 7.5 `story_corner` — 사연 (사연토크)

| 요소 | 내용 |
|---|---|
| 입력 | `board_story` 풀(오늘 주제와 맞는 후보). 실시간 `message`는 넣지 않는다(U11) |
| 단계 | ① 코너 콜 → ② [사연 낭독 → DJ 리액션·이야기 → 채팅 반응 인용] ×1~2 → ③ 마무리 |
| 출력 | 사연당 멘트 2~3개 |
| 전환 | 항목 소진 또는 예산 초과. 풀이 비면 `topic_talk`로 대체 |
| 계약 | `board_story: FEATURE`, `chat: STEER`, `message: DEFER(text_corner)` |

사연은 미리 쌓여 있으므로 ①·② 첫 멘트는 코너 진입 전에 **선생성**할 수 있다(버퍼 방어). 채팅 인용이 들어가는 단계만 진입 후 생성한다.

### 7.6 `dj_vs_listeners` — DJ 대 청취자 게임 (사연토크)

게스트와 겨루는 게임형 코너를 AI 혼자 진행할 수 있게 바꾼 것. 게스트 대신 **청취자 투표**와 DJ의 선택이 일치하는지 겨룬다.

| 요소 | 내용 |
|---|---|
| 입력 | 고민 사연(양자택일형 `board_story` — 태그로 구분 `[미정]`, 부족하면 엔진이 주제에서 생성), `vote` |
| 단계 | ① 코너 콜 + 규칙 설명 → ② [고민 낭독 + 선택지 제시 → **투표 창 열림** → DJ 이야기(투표 창과 겹침) → DJ 선택 공개 + 투표 결과 → 반응(채팅 인용) → 점수] ×3~5 → ③ 최종 점수 + 마무리 |
| 상태 | `score: {match, mismatch}` |
| 전환 | 항목 소진 또는 예산 초과 |
| 계약 | `vote: SOLICIT`, `chat: QUOTE`, 나머지 DEFER |

- **DJ의 선택은 투표 결과를 보기 전에 정해 저장한다.** 선택지 제시 멘트를 만들 때 LLM이 고르게 하고(구조화 출력), 결과 공개 멘트에서 그 값을 쓴다. 공정성과 재현성 때문이다.
- 투표 창(60초 `[예시]`) 동안 방송이 비지 않도록 DJ 이야기 단계(20~40초)와 겹치게 연다.

### 7.7 `topic_talk` — 주제 토크 (사연토크·음악의 `artist_talk` 변형)

| 요소 | 내용 |
|---|---|
| 입력 | 오늘의 주제(또는 다음 곡 아티스트·장르), QuotePool |
| 단계 | ① 화제 꺼내기(청취자에게 질문 던지기 포함 가능 — SOLICIT 질문형) → ② [이야기 + 채팅 인용] ×2~4 |
| 전환 | 예산 초과. STEER가 일어나면 남은 단계의 화제가 바뀐다 |
| 계약 | `chat: STEER`(사연토크) / `chat: QUOTE`(음악 `artist_talk`), 나머지 DEFER |

채팅이 없을 때(풀이 비었을 때) 진행 방식은 기존 persona의 "침묵 시 진행"을 이 코너의 단계 규칙으로 옮긴다 — 인용 없이 주제 이야기를 이어간다.

### 7.8 뉴스 코너: `headline` · `section` · `recap`

| 코너 | 입력 | 단계 | 계약 |
|---|---|---|---|
| `headline` | 수집 소재 상위 3건 | ① 헤드라인 3개 요약 | 전부 CLOSED |
| `section` | 분야별 소재 2~3건 | ① 분야 콜 → ② [기사 요약 + 출처] ×2~3 | 전부 CLOSED |
| `recap` | 이번 순환에서 다룬 기사 | ① 핵심 정리 | 전부 CLOSED |

모두 6.4절의 제약(`subjectivity: none`, `source_required: true`)을 가진다. 소재가 없으면 기존처럼 다음 코너로 넘어간다.

### 7.9 `filler` (공통)

버퍼 방어용 짧은 멘트. 코너가 아니라 편성 관리자가 버퍼 부족 시 끼우는 **단계**로 격하한다. 현재 코너의 `Thread`를 소재로 써서 흐름을 끊지 않는다.

### 7.10 접착 요소 (권장 이름: `GlueBank`)

코너 콜, 코너 마무리, 슬로건, 1부/2부 전환처럼 매번 같은 문구는 **방송 시작 시 한 번 생성·합성해 고정**한다.

- 기존 `ack.py`의 사전 렌더 캐시를 이 용도로 바꾼다
- 방송 시작 시 persona로 문구를 LLM 생성(1회) → L2 → TTS → 캐시. 같은 방송 안에서는 같은 오디오를 다시 쓴다
- 지연이 0이므로 코너 진입 직후 버퍼 공백을 메우는 역할도 한다

## 8. 호스트 커스터마이즈 (D4)

호스트는 방 생성 폼에서 **형식 → 형식별 선택지 → 참여 강도**를 고른다. 반영 모드는 바꿀 수 없다.

| 형식 | 호스트가 고르는 것 |
|---|---|
| `music` | 장르 취향(persona `music_taste`), 신청곡 받기 on/off, 참여 강도 |
| `talk` | 본 코너 2~3개 (`story_corner`, `text_corner`, `topic_talk`, `dj_vs_listeners` 중), 오늘의 주제, 참여 강도 |
| `news` | 분야 2~3개 (종합/경제/IT/스포츠/문화 `[예시]`) — 참여 강도 없음 |

### 8.1 참여 강도

참여 강도는 반영 모드 안의 손잡이를 묶은 **프리셋**이다. 호스트에게는 세 단계로만 보인다.

| 손잡이 | 낮음 | 보통 | 높음 |
|---|---|---|---|
| 세그먼트당 인용 상한 | 1 | 1 | 2 |
| 인용 간 최소 간격 | 120초 | 60초 | 30초 |
| 코너당 STEER 상한 | 0 | 1 | 2 |
| `topic_talk` 질문 던지기 | 없음 | 코너당 1회 | 코너당 1회 |
| `text_corner` 건수 | 3 | 4 | 5 |

전부 `[예시]`다. **선별 기준과 창 길이 W는 참여 강도에 넣지 않는다** — 실험 조작 변수이므로 연구자만 바꾼다(10절).

### 8.2 persona와의 경계

- persona는 **표현 층**(말투, 이름, 컨셉, 예시 멘트, 입버릇, 금지, 목소리, 선곡 취향)만 갖는다
- 기존 persona.md의 `BehaviorSpec`(행동 층)은 폐지한다. 그 필드들은 형식 계약·참여 강도·실험 조건으로 흩어진다(13절 대응표)
- 이유: 반영 방식이 코너마다 다르므로 persona 하나에 붙어 있을 수 없다. 기존의 "표현 층은 실험 간 고정, 행동 층은 조작 변수" 원칙은 "persona는 실험 간 고정, 선별 기준은 조작 변수"로 그대로 이어진다

### 8.3 실험 세션

실험용 방은 연구자 프리셋으로 잠근다 — 형식 `talk`, 코너 구성 고정, 참여 강도 고정, 선별 기준·W·결합 방식만 조건별로 다르게. 호스트 폼을 거치지 않는다.

## 9. 반영 확인 재설계 (D5: 요청별 ack 폐지)

기존 ack는 두 기능을 하나로 묶고 있었다 — (1) 요청자에게 "받았다"를 알리는 것, (2) 방송에서 요청자를 인정하는 것. 이를 분리한다.

### 9.1 접수 피드백 → UI

요청자 본인에게만, 즉시, 항상 보낸다. 엔진이 라우팅 결과를 상태로 통보하고 백엔드가 UI에 표시한다.

| 상태 | UI 표시 예 `[예시]` |
|---|---|
| `POOLED` | "DJ가 채팅을 보고 있어요" |
| `INBOXED` | "다음 문자 소개 시간 후보예요" / "곡 소개 때 소개될 수 있어요" |
| `COLLECTED` | "투표에 반영됐어요" |
| `HELD` | "곡이 끝나면 DJ가 볼 수 있어요" |
| `NOT_ON_AIR` | "이 방송은 채팅을 방송에 반영하지 않아요" (뉴스) |
| `REFLECTED` | "방송에 나왔어요" + 재생 시각 |
| `EXPIRED` | "이번엔 소개되지 못했어요" |
| `REJECTED` | "방송에 내보낼 수 없는 내용이에요" |

### 9.2 방송에서의 인정 → 집계 단위

특정 개인을 위한 접수 멘트는 없다. 대신 다음 두 가지를 결정적 트리거로 소재에 붙인다.

| 장치 | 트리거 `[예시]` | 예 |
|---|---|---|
| **집계 언급** | 최근 W 동안 풀에 N=8건 이상 쌓이고, 같은 키워드 비중이 높을 때 | "채팅창이 쇼핑 얘기로 뜨겁네요" |
| **예고** | `text_corner` inbox가 M=5건 이상이고 그 코너가 클락상 다음 두 코너 안에 없을 때 | "문자 많이 와 있어요, 이따 문자 소개 시간에 읽을게요" |

- 집계 언급·예고는 개인 반영(①단계)으로 세지 않는다. 별도 이벤트로 로그를 남긴다 — 생략된 요청자의 경험에 영향을 주는지가 측정 대상이다(10절 RQ-A 보조)
- 둘 다 세그먼트당 1회, 코너당 1회 상한 `[예시]`

### 9.3 입력 상태 머신

```
RECEIVED ─L0─┬→ REJECTED
             ├→ NOT_ON_AIR                                   (뉴스 형식)
             └→ ROUTED ─┬→ POOLED ──┬→ SELECTED → GENERATING → GENERATED → (백엔드) PUBLISHED → segment.started
                        ├→ INBOXED ─┤      │                                                    └→ REFLECTED
                        ├→ COLLECTED┘      └→ (생성 실패·인용 누락) POOLED/INBOXED 복귀 또는 EXPIRED
                        └→ HELD → (다음 코너 진입 시 재라우팅)
              POOLED/INBOXED ─(창 경과·방송 종료)→ EXPIRED
              L1 REJECT(입력 때문) → REJECTED
```

- `REFLECTED`는 그 입력을 반영한 세그먼트의 **재생 시작 통보(`segment.started`)** 를 받은 시각에 확정한다(12절). 측정 시각은 청취자 기기의 실제 재생 시각이 아니라 **서버 방송 시간 기준**이고, 인용 구절이 아니라 **그 구절이 들어 있는 세그먼트의 시작 시각**이다. 인용이 세그먼트 중간에 있으면 `quote_age`는 실제보다 그만큼 작게 잡힌다 — 세그먼트가 15~45초이므로 이 오차를 보고에 밝힌다
- 세그먼트 상태 이벤트의 역할: `PUBLISHED`(HLS 공개) = 방송 맥락 기록 기준([context-memory.md](context-memory.md) 3.1), `segment.started`(서버 방송 시간상 재생 시작) = `REFLECTED`·`L_reflect`·`quote_age`, `PLAYED`(서버 방송 시간상 재생 완료) = 기존 의미 유지
- `GENERATING`/`GENERATED`는 FEATURE·READ처럼 입력 하나가 세그먼트 하나를 차지할 때 의미가 있고, QUOTE처럼 여러 입력이 한 세그먼트에 섞일 때는 세그먼트 단위로 추적한다

### 9.4 반영 단계와 지연 재정의

| 단계 | 정의 | 해당 모드 |
|---|---|---|
| ① 언급 | 입력이 방송에서 개별적으로 언급됨 | QUOTE, READ, FEATURE, SOLICIT 대표 인용 |
| ② 리액션 | DJ가 입력 내용에 반응·답함 | QUOTE(한 문장 반응), READ, FEATURE |
| ③ 흐름 변경 | 입력 때문에 방송 흐름이 바뀜 | STEER, 신청곡 재생, 투표 결과로 곡·게임 결과 결정 |
| ④ 회상 | 앞서 반영된 입력을 이후 멘트에서 다시 꺼냄 | `closing` 돌아보기, 방송 맥락(context-memory.md) |

| 기호 | 정의 | 대체 |
|---|---|---|
| **L_ui** | 입력 도착 → 라우팅 상태 UI 표시 | 기존 L_ack(방송) 폐지 |
| **L_reflect** | 입력 도착 → 그 입력을 반영한 세그먼트 재생 시작 | 기존 L_res |
| **quote_age** | 인용 세그먼트 재생 시작 시각(`segment.started`) − 입력 도착 시각 | 신설 (QUOTE 전용) |
| **topic_match** | 인용 재생 시점에 입력의 화제가 아직 진행 중이었는지 (0/1) | 신설 — Q-02(반응 시점의 적절성) 지표 후보 |

## 10. 연구 설계 초안 (D2) `[확정 전]`

기존 RQ1~3의 문제의식(공유 스트림에서 반영의 상충, 버퍼와 지연의 상충)은 이어받고, 조작 변수를 새 구조의 손잡이로 바꾼다.

### 10.1 RQ-A: 선별 기준과 세 집단의 경험 (기존 RQ2 계승)

> 공유 스트림에서 실시간 채팅을 인용으로 반영할 때, **선별 기준**에 따라 (a) 반영된 요청자, (b) 반영되지 못한 요청자, (c) 비요청 청취자의 경험은 어떻게 달라지는가?

- **조작**: `QuoteSelector`의 기준 — 최근성 우선 / 화제 관련성 우선 (+ 다양성 우선 `[후보]`)
- **예상 방향**: 관련성 우선은 방송 흐름이 매끄러워 (c)에 유리하지만, 화제에서 벗어난 채팅이 계속 만료되어 (b)가 특정 유형(새 화제 제안, 엉뚱한 농담)에 쏠린다. 최근성 우선은 (b)가 고르게 분포하지만 흐름이 끊긴다
- **집단 분류**: 로그에서 자동 — REFLECTED가 1건 이상이면 (a), 입력은 했지만 전부 EXPIRED면 (b), 입력이 없으면 (c)
- **보조 조건 후보**: 9.2절 집계 언급·예고 on/off — 방송 차원의 집계 인정이 (b)의 무응답 경험을 완화하는가 (기존 RQ2 보충 3의 "공개적 인정" 질문을 이어받음)

### 10.2 RQ-B: 버퍼와 신선도의 상충 (기존 RQ1·RQ3 통합, 시스템 실험)

> 버퍼 크기와 인용 결합 방식이 방송 연속성과 인용의 시의성에 어떤 영향을 미치는가?

- **조작**: 목표 버퍼(초) × 결합 방식(선결합 / 지연 결합, 5.1.2절)
- **측정**: 언더런율, `quote_age`, `topic_match`, 인용 누락률
- **부하**: 합성 채팅 부하(F-18)로 도착률을 스윕한다 — 사람 없이 자동 실행

### 10.3 공통

- 사용자 실험은 **사연토크 형식 하나로 고정**한다(8.3절). 음악·뉴스는 시연과 구조 검증용
- persona(표현 층)·코너 구성·참여 강도·안전 계층은 조건 간 고정
- **측정**: 입력별 상태 전이 로그(9.3절), 반영 단계 도달 로그(9.4절), 행동 지표(재입력, 이탈 — F-32), 곡간 짧은 설문(F-33)
- **Q-01~03 지표 후보**: Q-02 ↔ `topic_match`, Q-03 ↔ 코너 전환 구간의 버퍼 공백·filler 투입 횟수 `[미정]`

```
config/formats/{music,talk,news}.yaml
```

### 11.2 메인 루프 (개념)

```
while 방송 중:
    if 버퍼 충분 or 동시 생성 상한: 대기
    job = current_corner.next_job(ctx)          # 코너가 계약에 따라 풀·inbox에서 소재를 꺼낸다
    if job is None:                             # 코너 종료
        current_corner = clock.next_corner()
        라우터.재라우팅(HELD)                   # 새 코너 계약으로
        job = glue.corner_call(current_corner)  # 사전 렌더 문구로 공백 없이 진입
    if 버퍼 위험: job = filler(current_corner.thread)
    생성(job)
```

`SchedulingPolicy.decide`(코너냐 요청이냐의 전역 결정)는 없어진다. 요청이 언제 반영될지는 **코너 계약이 정하고**, 무엇이 반영될지는 **선별기가 정한다**.
