**엔진이 하지 않는 것** — 방송 클럭, 믹싱/크로스페이드, HLS 서빙, 언더런 방어의 최종 책임(폴백 재생 실행), 입력의 최초 수신, 투표 집계, **곡 선정과 YouTube 재생**(F-34)은 스트리밍 백엔드 담당이다. 엔진은 오디오+메타데이터를 **제출**하는 생산자이고, 백엔드가 방송 시간축의 소유자다.

**상태 머신에서의 담당 구간** — 기획서 5.4절의 **입력 상태 머신은 엔진이 소유**한다(RECEIVED → … → REFLECTED/EXPIRED/REJECTED). 세그먼트 상태는 `GENERATING → GENERATED`까지 엔진, `MIXING` 이후는 백엔드 소유다. 입력의 `REFLECTED`는 그 입력이 들어간 세그먼트의 재생 시작 통보(`segment.started`, 서버 방송 시간 기준)를 백엔드에서 받아 엔진이 확정한다. `REJECTED` 판정은 L0~L2 어느 계층에서든 엔진이 내리고 백엔드에 통보한다.

## 2. 설계 원칙

1. **미정 사항은 설정과 인터페이스 뒤로** — 코너 구성은 형식별 설정 파일(`config/formats/*.yaml`)로, 선별 기준은 `QuoteSelector` 인터페이스 뒤에 둔다. 코너를 더하거나 수치를 바꿀 때 엔진 본체는 수정하지 않는다.
2. **고르는 것은 규칙, 말하는 것은 LLM** — 무엇을 인용·낭독할지, 언제 화제를 바꿀지는 편성 관리자가 결정적으로 정하고 로그를 남긴다. 프롬프트로 "적당히 골라서 읽어라"라고 지시하지 않는다.
3. **파이프라인은 단계(stage)로 분해** — 프롬프트 구성 → LLM → 인용 검사 → L2 검사 → TTS → 패키징을 독립 단계로 나누고, LLM/TTS 제공자는 어댑터로 격리해 교체 가능하게 한다.
4. **관통 우선, 품질은 교체** — 모든 단계는 처음부터 더미 구현(하드코딩 대본, 미리 만든 오디오)을 갖는다. 실제 구현은 더미를 하나씩 교체하는 방식으로 들어간다.
5. **계측은 처음부터** — 입력 상태 전이·선별 결과·생성 지연 기록은 실험 데이터(RQ-A, RQ-B)의 원천이므로, 나중에 붙이는 부가 기능이 아니라 파이프라인의 기본 동작으로 넣는다.
6. **되돌릴 수 없는 경계 이전에 안전 검사 완료** — L0~L2는 전부 엔진 내부, 즉 세그먼트 제출 이전에 끝난다. 제출된 오디오에는 부적절 콘텐츠가 없다는 것이 엔진이 백엔드에 제공하는 계약이다.

## 3. 전체 구조

```
                        ┌──────────────────────────────────────────────────────┐
                        │                    Station Engine                     │
                        │                 (스테이션당 1 인스턴스)                 │
  [RSS/피드] ──수집──→  │  ┌──────────┐                                        │
                        │  │ 소스 수집기│──소재──────────────┐                    │
                        │  └──────────┘                    ▼                    │
  입력 이벤트 ──────→   │  ┌──────────────┐   ┌──────────────────────────┐      │
  (백엔드 발행)          │  │ InputRouter  │──→│ QuotePool · Inbox · Held │      │
                        │  │ (L0, 계약 조회)│   └────────────┬─────────────┘      │
                        │  └──────────────┘                │ QuoteSelector      │
                        │                                  ▼                    │
  백프레셔/상태 통보 ──→ │  ┌──────────────────────────────────────────┐        │
  (백엔드 발행)          │  │ 편성 관리자 (Scheduler)                   │        │
                        │  │  Clock → CornerRun.next_job(ctx) / filler │← GlueBank
                        │  └──────────────────┬───────────────────────┘        │
                        │                     │ GenerationJob (단계 + 고른 입력)  │
                        │  ┌──────────────────▼───────────────────────┐        │
                        │  │ 생성 파이프라인                            │        │
                        │  │ 프롬프트 구성 → LLM(L1) → 인용 검사         │        │
                        │  │   → L2 검사 → TTS → 패키징                 │        │
                        │  └──────────────────┬───────────────────────┘        │
                        │  ┌────────┐         ▼                                │
                        │  │ 계측 로그│   ┌──────────┐                           │
                        │  │(SQLite) │   │  제출기   │ ──── 제출 ────→ [스트리밍 백엔드]
                        │  └────────┘   └──────────┘                            │
                        └──────────────────────────────────────────────────────┘
```

- **Station Engine**은 스테이션(방)당 1개 인스턴스로 기동한다(F-25). **다중 스테이션 동시 운영은 검증 필수 범위다**(확인 9 결정). 상위의 **EngineManager**가 백엔드가 발행하는 방 생성/종료 이벤트(`station.created`/`station.closed`)에 따라 StationEngine 인스턴스를 기동·종료한다(구현됨, #55).
- 런타임은 **Python + asyncio 단일 프로세스**를 기본으로 하고, 한 프로세스 안에서 EngineManager가 여러 StationEngine을 비동기 태스크로 구동한다. LLM/TTS 호출이 전부 I/O 바운드이므로 검증 목표 규모(소수의 동시 스테이션)에는 단일 프로세스로 충분하며, 프로세스 분리는 그 규모를 넘을 때 검토한다.
- **비용 상한**: 동시 생성 개수 제한을 스테이션별 상한과 **전역 상한** 두 층으로 둔다. 빈 방도 생성 비용을 계속 소비하는 문제(기획서 10장 리스크)에 대한 엔진 쪽 최소 방어선이다.

### 3.1 핵심 제어 흐름

편성 관리자가 유일한 의사결정 지점이다. 루프는 다음과 같다([CORNER_DESIGN.md](CORNER_DESIGN.md) 11.2절):

```
while 방송 중:
    if 버퍼 충분 or 동시 생성 상한: 대기
    job = current_corner.next_job(ctx)          # 코너가 계약에 따라 풀·inbox에서 소재를 꺼낸다
    if job is None:                             # 코너 종료
        current_corner = clock.next_corner()
        router.reroute(HELD)                    # 새 코너 계약으로 다시 라우팅
        job = glue.corner_call(current_corner)  # 사전 렌더 문구로 공백 없이 진입
    if 버퍼 위험: job = filler(current_corner.thread)
    생성(job)
```

- 기존 `SchedulingPolicy.decide`(코너를 진행할지 요청을 끼워 넣을지의 전역 결정)는 없어진다. 입력이 **언제** 반영될지는 코너 계약이, **무엇이** 반영될지는 선별기가 정한다.
- LLM은 "무엇을 말할지"를 결정하지 않는다. 편성 관리자가 칸과 소재를 정하고 LLM은 칸을 채운다(기획서 5.1의 핵심 설계 유지).
- 파이프라인 실행은 비동기 태스크이므로, 편성 관리자는 생성 완료를 기다리지 않고 다음 판단을 할 수 있다(선생성/버퍼 축적). 동시 생성 개수는 설정으로 제한한다(비용 상한).

## 4. 핵심 컴포넌트

### 4.1 편성 관리자 (Scheduler)

**입력**: 클락, 현재 `CornerRun`, 입력 풀·inbox, 백엔드가 통보하는 큐 잔량·백프레셔·곡 시간, 자체 생성 지연 통계.
**출력**: `GenerationJob` (어느 코너의 어느 단계를, 어떤 소재와 어떤 청취자 입력으로, 어떤 우선순위로 생성할지).

- **버퍼 관리만 남는다.** 코너 진행 순서는 클락과 `CornerRun`이, 입력 선택은 선별기가 가진다. 편성 관리자는 "지금 생성할지"와 "버퍼가 위험하면 filler를 끼울지"만 정한다.
- **곡 시간 반영** — 버퍼 계산(`generated_buffer_sec`)은 멘트 오디오 길이만 세므로, `track.started`의 곡 재생 시간을 더하도록 고쳐야 한다(4.8절). 그렇지 않으면 곡이 나가는 동안 멘트가 바닥난다고 착각해 필요 이상으로 생성한다.
- **재배치 규칙**: 엔진이 소유한 상태(GENERATING, 제출 전 GENERATED)만 재배치·취소할 수 있다. 제출된 세그먼트는 건드리지 않는다. GENERATING 취소는 "LLM/TTS 호출 결과를 버리는 것"으로 구현한다(API 호출 자체의 중단은 시도하지 않음 — 단순함 우선, 비용은 로그로 관찰).

### 4.2 입력 라우팅과 선별 — 연구 확장점

입력 처리는 두 부분으로 나뉜다. 세부 규칙은 [CORNER_DESIGN.md](CORNER_DESIGN.md) 4~5절.

**InputRouter** (권장 이름) — 입력이 도착하면 L0 검사 → 형식이 그 종류를 받는지 확인 → 현재 코너 계약 조회 → 해당 저장소로 보낸다.

```
QUOTE / STEER → QuotePool       → POOLED
READ          → inbox[READ]      → INBOXED
FEATURE       → inbox[해당 코너] → INBOXED
SOLICIT       → 열린 수집 창     → COLLECTED   (창이 없으면 QUOTE와 같게)
DEFER         → 그 모드를 가진 다음 코너의 inbox → INBOXED
CLOSED        → 보류 큐          → HELD        (다음 코너 진입 시 재라우팅)
형식이 받지 않음                   → NOT_ON_AIR  (뉴스 형식)
```

- 라우팅 결과는 즉시 `request.state`로 백엔드에 통보한다 — 요청자 UI 피드백(L_ui)의 원천이다.
- QuotePool은 코너가 바뀌어도 유지하되, 창(W)이 지나면 만료되므로 앞 코너의 채팅이 오래 남지 않는다.

**QuoteSelector** (권장 이름) — 인용을 허용하는 코너의 토크 단계가 세그먼트 생성을 시작할 때 풀에서 0~2건을 고른다. **RQ-A의 조작 지점**이다.

```python
class QuoteSelector(Protocol):
    def select(self, pool: QuotePool, thread: Thread, limits: QuoteLimits, now: float) -> Selection: ...
    # Selection = {selected, candidates_with_scores, expired} — 전부 selection_log에 남긴다
```

- 구현체는 점수 기준별로 하나씩 둔다 — `RecencySelector`, `RelevanceSelector`, `DiversitySelector` `[후보]`. 어떤 구현체를 쓸지는 스테이션 설정의 실험 조건으로 주입하고 방송 중에 바꾸지 않는다(확인 8).
- 화제 관련성은 **키워드 겹침(형태소 기반)** 으로 계산한다(결정 2026-10-12, CORNER_DESIGN U1) — 지연 0, 외부 호출 없음. 임베딩 유사도는 M6에서 비교 실측만 한다. 배치 LLM 분류는 비결정적이라 쓰지 않는다.
- 일반 방(실험 아닌 방)의 기본값은 화제 관련성 우선 + 선결합이다(U12).
- **선별에서 빠지고 창이 지난 입력이 RQ-A의 (b)** 다. 생략 결정도 반드시 기록한다(7장 `selection_log`).
- **집계 언급·예고** — 풀·inbox 상태가 트리거 조건을 만족하면 편성 관리자가 다음 멘트 소재에 "집계 언급"(예: 채팅이 같은 키워드로 몰림) 또는 "예고"(문자가 쌓였는데 문자 소개 코너가 멀다)를 붙인다. 개인 반영으로 세지 않고 별도 이벤트로 로그를 남긴다.

### 4.3 형식 · 클락 · 코너 — 편성 확장점

코너는 코드가 아니라 **설정(데이터)** 으로 정의하고, 엔진은 그 정의를 실행하는 상태 머신을 갖는다.

```python
class CornerSpec:                       # config/formats/*.yaml에서 로드
    corner_type: str
    steps: list[StepSpec]               # 진행 규칙 — 항목 루프는 StepSpec.repeat로 표현
    contract: dict[InputKind, Mode]     # 입력 계약
    constraints: Constraints            # 예: subjectivity=none, source_required
    budget_sec: tuple[int, int]         # 클락이 배정하는 시간 범위
    exit: ExitRule                      # 전환 조건

class CornerRun:                        # 방송 중 코너 1회 진행의 상태
    spec: CornerSpec
    step_index: int
    items: list                         # 이 코너가 소비할 항목 (사연, 문자, 투표 주제 …)
    thread: Thread                      # 화제 상태 — topic, keywords, recent_lines
    state: dict                         # 코너 고유 상태 (예: 게임 점수)
    started_at: float
    def next_job(self, ctx) -> GenerationJob | None   # None = 코너 종료
```

**형식별 코너** (결정 D1 — MVP 3종). 이름은 **권장 이름**이다. 코너별 입력·단계·계약은 [CORNER_DESIGN.md](CORNER_DESIGN.md) 7절.

| 구간 | 음악 (`music`) | 사연토크 (`talk`) | 뉴스 (`news`) |
|---|---|---|---|
| **오프닝** | (첫 곡) → `opening` | (첫 곡) → `opening` | (첫 곡) → `opening` |
| **순환** | `music_intro` → 곡, `artist_talk` | 호스트가 고른 본 코너 2~3개(`story_corner`·`text_corner`·`topic_talk`·`dj_vs_listeners`) 사이사이 `music_intro` → 곡 | `headline` → `section` ×2~3(사이 브릿지 곡) → `recap` |
| **엔딩** | `closing` → 마지막 곡(투표) | `closing` → 마지막 곡(투표) | `closing` → 마지막 곡 |
| **공통** | `filler`(버퍼 방어 단계), 접착 요소(`GlueBank`) | | |

- **첫 곡**은 호스트가 지정한 `first_song`이다. 방송 시작과 함께 **백엔드가 바로 튼다.** 엔진은 그동안 오프닝 멘트를 만든다 — 첫 멘트의 생성 지연을 곡이 가려 준다.
- **`opening`** 은 인사 + 첫 곡 백어나운스 → 오늘의 주제 → 코너 예고 + **참여 방법 안내**의 3단계다. 참여 방법은 형식·호스트 선택으로 정해진 계약에서 결정적으로 만든다.
- **`ClockBuilder`** (권장 이름, 기존 `RunningOrderBuilder` 대체)가 형식의 1회분 순환 틀을 `broadcast_minutes`(MVP 30~60분)에 맞춰 오프닝 + 순환 ×N + 엔딩으로 펼친다. 곡 길이는 `track.queued`의 `duration_ms`를 쓰고, 모르면 4분으로 가정한다. 수치는 모두 `[예시]`이고 단계 길이 실측 후 다시 계산한다.
- 방송 길이를 맞추는 것은 **엔딩 시작 시각**이다. 순환은 남은 시간이 엔딩 길이에 닿으면 멈추고 엔딩으로 넘어간다. 곡 재생 중에 그 시각이 오면 곡이 끝난 뒤 넘어간다.
- 소재가 없는 코너(사연 풀이 비었음, inbox가 2건 미만, RSS 캐시가 비었음)는 이번 차례를 건너뛰거나 대체 코너로 간다.
- DJ 스타일(F-25)은 코너가 아니라 **스테이션 설정**(persona 표현 층)이며, 모든 코너의 프롬프트에 공통 주입된다 ([persona.md](persona.md) 4절). 뉴스 형식에서는 persona의 유머·입버릇을 끈다.

### 4.4 생성 파이프라인

```
GenerationJob
  → [1] 프롬프트 구성   코너 단계 빌더 + persona + 직전 방송 맥락 요약 + Thread + 고른 입력(데이터 블록)
  → [2] LLM 호출        L1: 프롬프트에 "부적합 시 대본 대신 REJECT 출력" 지시 내장
  → [3] 인용 검사        고른 입력이 대본에 실제로 들어갔는지 문자열 대조 — 빠진 입력은 풀로 되돌린다(창이 남아 있을 때)
  → [4] L2 출력 검사     생성된 대본 텍스트에 금칙어/정규식 재검사 (뉴스 형식은 주관 표현 규칙 추가)
  → [5] TTS 호출        대본 → 오디오 파일
  → [6] 패키징          duration 실측, 메타데이터(input_refs, reflection_levels) 부여 → 제출기로
```

- 각 단계는 인터페이스로 분리하고, LLM/TTS는 provider 어댑터(`LlmClient`, `TtsClient`)로 격리한다. 더미 어댑터(고정 텍스트 반환, 미리 녹음된 wav 반환)를 처음부터 유지해 API 키 없이도 전체 파이프라인을 돌릴 수 있게 한다(테스트·부하 실험·발표장 폴백 겸용).
- **고른 입력을 넣었으면 반드시 인용하게 한다.** 인용할지 말지를 LLM에 맡기지 않는다 — 지시는 "아래 채팅을 '~라고 하신 분이 있네요'처럼 짧게 인용하고 한 문장으로 반응하라. 닉네임이나 ID를 말하지 않는다"로 고정한다.
- **[2]에서 REJECT가 나오면** — 입력 때문이면 그 입력을 REJECTED로 종결하고 백엔드에 통보한다(F-15). 코너 진행용 Job이 REJECT되면 filler로 대체한다.
- **[4] 뉴스 L2** — 평가어·출처 없는 전망·1인칭 의견을 검출하면 재생성 1회, 또 걸리면 소재 문장 요약 템플릿으로 대체한다 `[미정: 규칙 목록]`.
- **실패 처리(MVP 규칙)**: LLM/TTS 호출 실패·타임아웃 시 1회 재시도, 재실패 시 filler 대체. 고른 입력은 풀·inbox로 되돌린다. 정교한 재시도 전략은 실측 후 조정한다.
- 모든 단계 경계에서 타임스탬프를 기록한다(→ 7장 계측).
- **[1]의 방송 맥락은 최근 N개 세그먼트의 요약만 유지한다**(확인 10 결정). 방송 간 장기 기억(F-23)은 두지 않는다. N 초깃값은 8로 두고 프롬프트 길이·대본 품질 실측 후 조정한다. 코너 안의 연속성은 별도로 `Thread.recent_lines`가 맡는다.

### 4.5 접착 요소 사전 렌더 (`GlueBank`, 기존 ack 단축 경로 대체)

요청별 방송 ack는 폐지했다(결정 D5, 2026-10-12). 접수 피드백은 UI로(`request.state` 통보), 방송에서의 인정은 집계 단위로(4.2절) 옮겼다. 기존 ack 사전 렌더 캐시(`ack.py` `AckCache`)는 **접착 요소** 용도로 바꾼다.

- **대상** — 코너 콜, 코너 마무리, 슬로건, 1부/2부 전환처럼 매번 같은 문구, 그리고 곡 소개 멘트 생성이 실패했을 때 쓰는 짧은 고정 문구("이어서 한 곡 듣고 올게요" 류).
- **방식** — 방송 시작 시 persona로 문구를 LLM 생성(1회) → L2 → 그 방 보이스로 TTS → 캐시. 같은 방송 안에서는 같은 오디오를 다시 쓴다.
- **역할** — 지연이 0이므로 코너 진입 직후 버퍼 공백을 메운다(3.1절 루프의 `glue.corner_call`).
- 보이스가 방 생성 시 확정돼 있어야 하는 이유도 이것이다 — 사전 렌더가 방송 시작 전에 그 목소리로 이뤄진다. 사전 렌더 실패는 `station.rejected`(`tts_unavailable`)다.

### 4.6 안전 계층 (F-13)

| 계층 | 엔진 내 위치 | 구현 |
|---|---|---|
| L0 | InputRouter — 입력 이벤트 수신 직후 (게시판 사연 포함) | 금칙어·정규식(연락처, URL, 욕설, 특정인 지목). 룰은 코드가 아니라 데이터 파일(`safety/rules.yaml`)로 관리 |
| L1 | 프롬프트 구성 단계 | 대본 생성 프롬프트에 판단 지시 내장, 별도 LLM 호출 없음 |
| L2 | TTS 직전 | L0과 동일 룰셋 + LLM 산출물 특화 패턴 재검사. 뉴스 형식은 주관 표현 규칙 추가(4.4절) |

- L0 탈락 시 즉시 REJECTED 통보(풀·inbox 진입 없음). 안전 계층은 형식·코너·실험 조건과 무관하게 동일 적용하며, L0·L2 소요 시간을 계측해 보고한다(기획서 5.4의 요구).

### 4.7 소스 수집기 (F-04)

- RSS/피드를 주기 폴링해 로컬 캐시(SQLite 또는 JSON 파일)에 적재하는 독립 백그라운드 태스크. 뉴스 형식의 `headline`·`section`·`recap` 코너는 이 캐시만 읽는다 — **생성 경로에서 외부 네트워크를 기다리지 않는다**(지연 예측 가능성 확보).
- 호스트가 고른 분야(종합/경제/IT/스포츠/문화 `[예시]`)별로 피드를 나눠 둔다. 소재에는 출처 매체를 함께 저장한다 — 뉴스 형식은 출처를 밝혀야 한다.
- 수집 실패는 방송을 막지 않는다: 캐시가 비면 해당 코너는 건너뛰고 클락의 다음 코너로 넘어간다.

### 4.8 곡 — YouTube 재생 (결정 2026-10-08, F-17·F-34)

- **곡 선정과 재생은 백엔드**가 한다(F-34, YouTube 플레이리스트 서버 재생). 곡 출처는 플레이리스트, 청취자 신청곡(YouTube 링크), 호스트가 지정한 첫 곡, 투표로 정한 마지막 곡이다.
- **엔진은 곡을 고르지 않는다.** 백엔드가 다음 곡을 미리 정해 `track.queued`(제목·아티스트·길이)로 알려주면, 클락이 `music_intro`에 왔을 때 그 곡의 소개 멘트를 만들어 `music_ref`로 지정한다. **어떤 곡은 백엔드, 언제는 엔진**이다 ([ENGINE_REDIS_CONTRACT.md](ENGINE_REDIS_CONTRACT.md) 3.4절).
- **곡 시간** — 엔진은 `track.started`의 시작 시각과 `duration_ms`로 곡이 끝나는 시각을 안다. 버퍼 계산에 곡 재생 시간을 더한다(4.1절, 구현 항목). 곡 재생 중은 `music_intro` 계약상 CLOSED라 그동안 들어온 채팅·사연은 HELD로 두었다가 곡이 끝나면 다시 라우팅한다.
- **신청곡** — 전용 폼(곡 제목·아티스트·링크·한마디)으로 받고, 링크가 없으면 백엔드가 YouTube 검색 결과 중 청취자가 고르게 한다. 백엔드가 곡 정보로 풀어 `request.arrived`의 `track`에, 한마디는 `body`에 싣는다 ([ENGINE_REDIS_CONTRACT.md](ENGINE_REDIS_CONTRACT.md) 3.4절 — v2에서 `kind: "song_request"`, 10장). 신청곡은 `music_intro`의 FEATURE 입력이다 — 백엔드가 고른 다음 곡이 신청곡이면 신청자 닉네임과 한마디를 소재로 넣는다(반영 ③단계).
- **BGM과 더킹** (결정 2026-10-08) — MVP는 멘트 밑에 별도 BGM을 깔고 DJ가 말할 때만 줄이는 방식만 한다. 곡과 멘트는 겹치지 않으므로 엔진 변경은 없고, 믹싱은 백엔드가 한다. 실제 곡 위에 겹쳐 말하기(talk-over)는 MVP 이후로 미룬다 ([ENGINE_REDIS_CONTRACT.md](ENGINE_REDIS_CONTRACT.md) 3.6절, **[확인 14]**).
- **무드 신청은 폐지했다** (2026-10-12, 기획서 rev.11). 기분·상황 이야기는 채팅이나 사연 보내기로 들어온다.
- **카탈로그(`catalog.py`)는 로컬 개발·테스트용 더미로만 남긴다.** 무드 태그 매칭·라이선스 필드·카탈로그 조회 REST는 만들지 않는다 (확인 5 무효).
- 곡 제목·아티스트는 외부 텍스트(YouTube 메타데이터)이므로 프롬프트에는 데이터 블록으로만 넣는다.

## 5. 데이터 모델

인터페이스 계약(기획서 9장)의 엔진 쪽 구체화. 현재 구현은 계약 v1이고, 코너 재설계에 따른 변경은 **v2 개정안**([ENGINE_REDIS_CONTRACT.md](ENGINE_REDIS_CONTRACT.md) 10장)으로 백엔드 파트와 합의한 뒤 고정한다. 아래는 v2 기준이다.

### 5.1 세그먼트 제출 페이로드 (엔진 → 백엔드)

```json
{
  "id": "seg_01J9XK...",           // 엔진 발급 ULID
  "station_id": "st_001",
  "audio_ref": "st_001/seg_01J9XK.mp3",  // 공유 스토리지 상대 경로
  "duration_ms": 12400,             // 실측값
  "corner_type": "topic_talk",
  "kind": "speech",                 // speech | glue | filler  (v2에서 ack 폐지, 접착 요소는 glue)
  "priority": 50,
  "reorderable": true,
  "input_refs": ["req_abc123", "req_abc130"],  // 이 멘트가 반영한 입력들 (v1의 request_ref 단일 값 대체). 게시판 사연은 story_id
  "reflection_levels": {"req_abc123": 2, "req_abc130": 3},  // 입력별 반영 단계 (1~4). 입력이 없으면 {}
  "music_ref": "yt:dQw4w9WgXcQ",     // 이 멘트 바로 다음에 틀 곡 — 백엔드가 track.queued로 알려준 track_ref (4.8절)
  "created_at": 1789496813.26       // Unix 초 (계약 결정 2026-10-08)
}
```

### 5.2 백엔드 → 엔진 이벤트

| 이벤트 | 페이로드 요지 | 엔진의 반응 |
|---|---|---|
| `station.created` | 방송 시간, 첫 곡, 오늘의 주제, persona 본문, **형식·코너 선택·참여 강도·실험 조건** (v2) | EngineManager가 StationEngine 기동, 클락 구성, `GlueBank` 사전 렌더링 → `station.started`/`station.rejected` |
| `request.arrived` | 입력 id, **종류(`chat`\|`message`\|`song_request`)**, 본문, 요청자 ref, **닉네임**, 신청곡이면 곡 정보 (v2) | InputRouter: L0 검사 → 계약 조회 → 풀·inbox·보류 적재, 라우팅 결과를 `request.state`로 통보 |
| `backpressure` | D_total 현재값, 임계값, 심각도 | 버퍼 계산의 기준을 백엔드 실측 D_total로 바꾼다(#61 구현) |
| `state.transition` | 세그먼트 id, 새 상태(MIXING/PUBLISHED/PLAYED), 시각 | 재배치 가능 집합에서 제거, 방송 맥락 갱신(`PUBLISHED`), 계측(`PLAYED` = 재생 완료) |
| `segment.started` | 세그먼트 id, 서버 방송 시간상 재생 시작 시각 (v2 신설, 모든 세그먼트) | 받은 시점에 그 세그먼트의 `input_refs`를 REFLECTED로 확정. `L_reflect`·`quote_age`는 페이로드의 `started_at`으로 기록. 같은 세그먼트 재전달은 무시 (계약 10.6절) |
| `track.queued` / `track.started` | 다음에 틀 곡 정보 / 곡 재생 시작 시각 | 곡 소개 멘트 소재 / 곡 종료 시각을 버퍼 계산에 반영, 곡 끝나면 HELD 재라우팅 (4.8절) |
| `board.story` / `board.story.withdrawn` | 게시판 사연 / 다른 방에서 읽힌 사연 | L0 검사 → `story_corner`의 inbox 적재 / 제거 |
| `vote.result` | 투표 id, 선택지별 집계 (v2 신설) | 수집 창을 닫고 결과를 다음 단계 소재로 |
| `station.closed` | 스테이션 id, 사유(정상 종료/운영자 중단) | 진행 중 생성 취소, 남은 풀·inbox를 EXPIRED 처리, 인스턴스 종료, 계측 플러시 |

## 6. 백엔드와의 통신·배포 형태 (결정 — [확인 1])

기획서의 기술 스택 장은 rev.8에서 별도 문서로 이관되었다(문서 작성 예정). 백엔드가 큐·방송 상태 관리에 Redis를 사용하는 구상은 유지되고 있으므로 아래를 기본안으로 제안하되, 기술 스택 문서가 확정되면 그에 맞춰 갱신한다.

- **이벤트(양방향)**: Redis Streams (스테이션별 스트림 `engine:{station_id}:in` / `:out`). pub/sub 대비 재기동 시 유실이 없어 상태 머신 통보에 안전하다.
- **오디오 전달**: 단일 머신 배포 전제(발표장 로컬 서버 시나리오와 일치)로 **공유 파일 시스템 경로**를 페이로드에 담는다. 오브젝트 스토리지 도입은 하지 않는다.
- **세그먼트 제출**: 이벤트와 동일하게 Redis Stream으로 (파일 먼저 쓰고 메시지 발행).

HTTP API 방식(백엔드 FastAPI에 POST)도 가능하나, 백엔드→엔진 방향의 이벤트 푸시가 어쨌든 필요하므로 채널을 Redis 하나로 통일하는 편이 단순하다. **1주차 계약 회의의 결정 사항.**

> **결정 (2026-09-20)**: 위 제안대로 **흐름은 Redis Streams**, **오디오는 공유 파일시스템 경로**로 한다. 운영자 콘솔용 관측도 5.3의 `engine.health` 하트비트를 그대로 쓴다 — 버퍼 잔량·진행 중 생성 수·지연 P95에 러닝오더 위치, 정책 이름, 직전 주기의 결정 요약을 더해 발행한다. *(2026-10-12 갱신: v2에서 러닝오더 위치·정책 이름은 현재 코너·단계·실험 조건으로 바뀐다 — 계약 10장.)*
>
> 다만 **푸시로 감당이 안 되는 조회 5개**(`/health`, 전역 상태, 결정 로그, 곡 카탈로그 2개)는 엔진이 GET 전용 REST로 연다. *(2026-10-08 갱신: 곡 카탈로그 2개는 YouTube 전환으로 없앴고, 방 생성 화면용 persona 초안 생성 POST 2개를 추가했다 — 계약 6장.)* 결정 로그는 실측 초당 1.2~2.1건이라 스트림에 실으면 세그먼트 보존 구간을 깎아먹고, `ScheduleContext` 스키마가 실험 중 계속 바뀌어 계약에 묶기 어렵다. 곡 카탈로그는 정적 데이터라 푸시 대상이 아니다. 엔진이 포트를 여는 범위는 여기까지이며, 생산자 역할 자체는 그대로다.
>
> 스트림·envelope·전달 보장·오디오 파일 규칙, 하트비트 페이로드, 조회 REST 목록, 백엔드 파트 API 표와의 매핑은 [ENGINE_REDIS_CONTRACT.md](ENGINE_REDIS_CONTRACT.md)에 정리했다 (2026-10-08 미결 사항 확정 — 흐름과 `station.created`는 엔진 구현 완료, 하트비트·REST·곡·사연 이벤트는 미구현).

## 7. 계측 (실험 데이터의 원천)

- 엔진 로컬 SQLite(`engine_metrics.sqlite`)에 기록. 테이블 초안 (v0.5 — 코너 재설계 반영):
  - `generation_log`: job id, corner_type, step, `input_refs`, 각 파이프라인 단계의 시작/종료 시각, 토큰 수, 결과(ok/reject/fail/quote_missing)
  - `input_log` (기존 `request_log` 확장): 입력 id, 종류, `requester_ref`, 상태 전이 시각 전부(RECEIVED~REFLECTED/EXPIRED/REJECTED), 도달한 반영 단계. **L_ui·L_reflect·`quote_age` 계산과 RQ-A의 (a)/(b)/(c) 집단 분류의 원천**
  - `selection_log` (신설, 기존 `decision_log`의 정책 결정 역할 대체): 선별 시점, 코너·단계, 선별 기준(실험 조건), 후보 입력별 점수, 선택·제외·만료 결과, 당시 `Thread.topic`·`keywords`. **고르지 않은 것도 기록한다** — (b) 집단이 왜 빠졌는지의 근거다
  - `corner_log` (신설): 코너 진입·종료 시각, 실제 소요, 단계 수, 건너뛴 이유. 클락 수치 보정과 Q-03(코너 전환) 지표의 원천
  - `aggregate_log` (신설): 집계 언급·예고 이벤트 — 개인 반영으로 세지 않는다(RQ-A 보조 조건)
  - `decision_log`: 편성 관리자의 버퍼 판단(생성/대기/filler) 스냅샷. 엔진 REST 결정 로그 조회(계약 6.1절)가 이 테이블을 읽는다
- 백엔드·프론트 계측과의 조인 키는 `segment_id`/`request_id`(입력 id). 시계는 서버 시각 기준(엔진·백엔드 동일 머신 전제면 문제없음).
- `topic_match`는 인용 세그먼트의 재생 시작 시각(`segment.started`)과 그 시각의 `Thread` 상태를 대조해 사후 계산한다 — 판정 기준은 `[미정]`.
- 재생 시각은 모두 **서버 방송 시간 기준이고 세그먼트 단위**다. 인용 구절이 세그먼트 중간에 있어도 세그먼트 시작 시각을 쓰므로 `quote_age`는 그만큼 작게 잡힌다([ENGINE_REDIS_CONTRACT.md](ENGINE_REDIS_CONTRACT.md) 10.6절).

## 9. 단계별 구현 계획

기획서의 개발 일정 장은 rev.8에서 삭제되어 별도 일정 문서로 관리될 예정이다. 따라서 여기서는 **주차를 못 박지 않고 단계의 순서·내용·완료 기준만** 정의한다. 단계 전환은 날짜가 아니라 완료 기준 충족으로 판단한다([확인 11]). v0.5에서 M3 이후를 코너 재설계 기준으로 다시 짰다.

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| **M0 관통** | transport + 제출기 + 더미 파이프라인(하드코딩 대본, 미리 만든 오디오 3~4개 순환 제출) | 백엔드가 엔진 제출물을 받아 프론트에서 소리가 남. 계약 스키마 v1 고정 |
| **M1 생성 v1** | LLM/TTS 실어댑터, 임시 코너 3종(opening·music_intro·filler), 고정 러닝오더, L1/L2, 계측 기본 | 실생성 대본으로 30분 무개입 방송. 생성 지연 분포 첫 실측 리포트 |
| **M2 버퍼·안정성** | 선생성 버퍼 관리, 백프레셔 반응, briefing 코너+RSS, 실패 처리·filler 대체 | 3시간 무중단 (백엔드 통합 기준). D_total 임계 실측치 산출 |
| **M3 코너 구조 전환** | `format/`(CornerSpec·loader·ClockBuilder), `CornerRun`·`Thread`, 형식 3종 yaml, `GlueBank`, 곡 이벤트(`track.queued`/`started`)와 버퍼 계산의 곡 시간 반영, 계약 v2 협의 | 입력 없이 형식 3종 각각 30분 방송이 클락대로 진행. 다중 스테이션 동시 방송 유지 |
| **M4 입력 반영** | `InputRouter`·풀·inbox·보류, QUOTE/READ/FEATURE, 입력 상태 통보(v2 `request.state`), 인용 검사, `corner.changed`, 게시판 사연(`board.story`), REFLECTED 확정 | 사연토크 방송에서 채팅 인용·문자 낭독·게시판 사연·신청곡이 계약대로 반영되고 요청자 UI 상태가 전부 맞음. L_ui·L_reflect 첫 실측 |
| **M5 상호작용 확장** | STEER, SOLICIT(질문형·투표 — `vote.open`/`vote.result`), `dj_vs_listeners`, 집계 언급·예고, 뉴스 L2 주관 표현 규칙 | 형식 3종의 코너 풀 전부 동작. 뉴스 형식에서 채팅이 NOT_ON_AIR로 처리됨 |
| **M6 실험** | 선별 기준 구현체 2~3종, 화제 관련성 계산 비교(키워드/임베딩), 실험 프리셋, `selection_log`·`corner_log`·`aggregate_log`, 지연 결합(백엔드 지원 시), 부하 생성기(F-18) 연동 훅 | 실험 조건 교체가 설정 1줄로 가능. RQ-B 자동 스윕에 필요한 입출력 완비 |

각 단계는 이전 단계의 더미/임시 구현을 교체하는 방식이다. M3에서 기존 `RunningOrder`·`SchedulingPolicy`·`request_reply` 코너·`ack.py`를 걷어낸다.
